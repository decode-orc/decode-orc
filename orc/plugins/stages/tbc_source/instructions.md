# TBC Source

Reads one or more TBC files produced by ld-decode or vhs-decode and presents the decoded video as a frame-domain representation for downstream stages. The stage detects the video system (PAL, NTSC, PAL-M; SECAM by the project's format, see below) and signal type (composite or Y/C) from the `.tbc.db` metadata database, remaps all sample levels from the ld-decode 16-bit internal domain to the 10-bit CVBS domain, and assembles full-frame buffers ready for processing.

## When to use

Add TBC Source as the first stage in any pipeline that starts from ld-decode or vhs-decode output. Select the composite `.tbc` file for a standard composite capture, or supply the `.tbcy` luma and `.tbcc` chroma files for a Y/C capture. The audio, EFM disc data and AC3 RF sidecars are set by their own path parameters. They are not searched for when the stage runs: when you pick the TBC file in **Edit Parameters...**, the dialog fills in any empty sidecar path for which a file with the same base name exists; from a script, set them explicitly. The metadata database must sit beside the TBC file (`<base>.tbc.db`, also for a `.tbcy`/`.tbcc` pair).

## Parameters

The file-path parameters offered match the project's source type: a composite project shows only **TBC File Path**, while a Y/C project shows only the **Luma** and **Chroma** paths.

| Parameter | Meaning |
|-----------|---------|
| TBC File Path (`input_path`) | Path to the composite `.tbc` file. Composite projects only. |
| Luma TBC File Path (`y_path`) | Path to the luma `.tbcy` file. Y/C projects only; set together with `c_path`. |
| Chroma TBC File Path (`c_path`) | Path to the chroma `.tbcc` file. Y/C projects only; set together with `y_path`. |
| PCM Audio File Path (`pcm_path`) | Path to the analogue audio `.pcm` sidecar (raw signed 16-bit stereo PCM as written by ld-decode). Always converted to 48 kHz 24-bit frame-locked audio on ingest. |
| Audio Channel Pair Name (`pcm_name`) | Human-readable name for the analogue audio channel pair; surfaces in the CVBS container and as the embedded stream title in the Video Sink. Empty uses "Analogue". |
| EFM Data File Path (`efm_path`) | Path to the EFM t-value `.efm` sidecar. |
| AC3 RF Symbols File Path (`ac3rf_path`) | Path to the AC3 RF symbols `.ac3sym` sidecar. |

## What it does

At execute time the stage opens the `.tbc.db` metadata database (falling back to legacy `.tbc.json` metadata produced by older ld-decode/vhs-decode versions) and reads the video system, field dimensions, and signal levels. It then selects the correct converter (PAL composite, PAL Y/C, NTSC composite, NTSC Y/C, or PAL-M composite) and reads each pair of TBC fields, remapping the 16-bit ld-decode levels to the 10-bit CVBS domain. The resulting full-frame buffers are assembled in order and returned as a VideoFrameRepresentation.

Frame sizes after assembly: PAL frames contain 709,379 samples; NTSC frames contain 477,750 samples; PAL-M frames contain 477,225 samples.

PAL frames are also moved onto the 4fsc subcarrier lattice the CVBS format defines. ld-decode stores PAL fields line-locked: every line is exactly 1135 samples with the line sync at the same sample position. A PAL line is 1135.0064 samples of the 4fsc clock, so the CVBS frame is one uniform grid of 709,379 samples on which the colour subcarrier keeps a fixed phase relationship to the sample index. The stage resamples each field onto that grid (a 16-tap interpolator, flat to within 0.2% up to 7 MHz). Each field comes out two samples longer, and those are the two extra samples that end frame lines 312 and 624. As a result a `.tbc` and a native ld-decode `.cvbs` of the same disc give the same frame, and decoders that rely on the lattice phase (PAL Still in particular) work on TBC input. Across each field the picture moves right by up to 2 samples (about 0.11 µs) relative to the stored TBC lines; dropouts recorded in the metadata move with it and are rounded outward so a marked region never shrinks. NTSC and PAL-M lines are a whole number of samples, so their line-locked and subcarrier-locked grids are the same and no line is resampled. NTSC frames are moved two samples earlier instead: ld-decode stores each NTSC line with the sync edge (0H) 1.4–1.9 samples after the line's first sample, and the CVBS format puts it just before (0.63 of a sample). The two positions sample the same subcarrier phases, so they are exactly two samples apart, and the whole frame moves by two; the frame's first two TBC samples (front porch, never in the picture) end the frame. Dropouts move with it. TBC Sink moves the samples back exactly, so an NTSC TBC Source → TBC Sink round trip puts every sample where it was; it differs from the original only by the 10-bit rounding every TBC import makes. PAL-M frames are copied unchanged: vhs-decode's PAL-M line start is not a constant distance from 0H, and the stage does not guess one. Stages that read only a few lines of each frame (VBI and caption decoding, the SNR and burst measurements, the Disc Mapper) get the same lines as the full frame, so on PAL they too see the lattice, not the stored TBC lines.

Colour-sequence IDs (the `colour_frame_phase` observer's field phase IDs, which Frame Map's `remove_duplicates` and `pad_gaps`, the Disc Mapper and the NTSC 3D decoders use) need a source that is subcarrier phase locked. The CVBS file format specification decides that from the file's declared signal state, but the TBC format is not part of that specification, so the stage decides it by video system. PAL and NTSC are treated as locked, whatever the metadata's `is_subcarrier_locked` says: the IDs measured on ld-decode PAL and NTSC `.tbc` files are exactly ld-decode's own, yet ld-decode writes `is_subcarrier_locked = 0` in its older `.tbc.db` files, and the specification's own example calls ld-decode's NTSC `.tbc` not phase locked. Reading either literally would make every ID unknown and turn the NTSC 3D decoders into 2D on all TBC input. PAL-M is treated as locked only when a `.tbc.db` declares `is_subcarrier_locked = 1` (TBC Sink writes the pipeline's lock state there). vhs-decode writes 0 for PAL-M and a `.tbc.json` declares nothing, so a vhs-decode PAL-M capture is unlocked and its IDs are unknown; the burst there follows no colour sequence.

**SECAM.** A TBC cannot say it carries SECAM: the ld-decode schema has no SECAM system, and vhs-decode writes `PAL` for SECAM and MESECAM captures. So the project decides. In a SECAM project a 625-line TBC (labelled `PAL`) is read as SECAM, and the stage logs that it is doing so; the samples are exactly those a PAL project gets, moved onto the same 4fsc lattice, because SECAM shares PAL's raster. A SECAM source is never subcarrier phase locked (the CVBS file format specification forbids it), so its colour-sequence IDs are unknown. A SECAM project refuses a 525-line TBC, and any other project refuses a TBC whose metadata says `SECAM`. The display name reads, for example, "SECAM TBC Composite". To decode a SECAM tape, create a SECAM project, or let Decode-Orc switch a PAL project that uses the `secam` decoder when it offers to.

NTSC-J sources are detected automatically from the metadata signal levels: when the recorded picture black sits at the 0 IRE blanking level instead of the standard 7.5 IRE setup pedestal, the stage reports the non-standard black level to downstream stages (exactly as a CVBS source with an explicit NTSC-J black level would). Fields the decoder marked as padding (`pad` in the TBC metadata, written when the player skipped) are honoured: a frame whose two fields are both padding is flagged as a padding frame, so the host observer pass records "padded, no data" instead of measuring the synthetic content, and padding-aware stages (stacker, TBC Sink) skip it. Colour-sequence phase is never taken from the TBC metadata — stages that need it measure it from the burst via the host colour-frame-phase observer. On NTSC that measurement, taken on the moved frame, gives the same field phase IDs ld-decode wrote. Dropouts recorded in the metadata are passed downstream as dropout hints; they are read from the metadata database field by field as frames are requested, not all at once when the source opens, so a long tape with many dropouts opens quickly. Associated audio (`.pcm`), EFM disc data (`.efm`), and AC3 RF (`.ac3sym`) sidecars are attached to each frame when their path parameters are set and the files exist.

When a `.pcm` sidecar is present it becomes audio channel pair 0 (named from `pcm_name`, default "Analogue"). The sidecar — raw signed 16-bit little-endian stereo PCM, nominally 44100 Hz as written by ld-decode — is always converted on ingest to the pipeline's only audio form: 48 kHz synchronous (frame-locked) 24-bit stereo, per SMPTE 272M. Samples are widened to 24-bit and resampled with SoXR HQ (duration- and sync-preserving) for all systems, including PAL. The conversion is deferred until audio is first read, so video-only preview never pays for it. It then runs only as far ahead as the frames being read, a block of about 1.5 seconds at a time, into a cache file on disk (about 1.4 GB per hour of audio, removed when the source is released), so memory use does not depend on the length of the capture and the first frame is not held up by the rest of the tape. The cache goes in the per-user cache directory (`~/.cache/decode-orc/audio` on Linux, `~/Library/Caches/decode-orc/audio` on macOS, `%LOCALAPPDATA%\decode-orc\cache\audio` on Windows); set the `ORC_AUDIO_CACHE_DIR` environment variable to put it elsewhere (or `ORC_CACHE_DIR`, which moves every decode-orc scratch file, to put it in an `audio` directory under that). When the TBC metadata records the PCM parameters, the declared sample rate is honoured as the resampler input rate; an unsupported layout (unsigned, big-endian, or a bit depth other than 16) raises an error observation and disables audio.

The raw `.efm` sidecar stores one byte per EFM T-value in field order; the stage locates each frame's T-values using the per-field T-value counts recorded in the `.tbc.db` metadata. (Unlike CVBS captures, TBC captures have no separate `.efm.meta` index — the counts in the video metadata are authoritative.) EFM is therefore exposed to downstream stages, such as the EFM Sink, only when both the `.efm` file exists and the metadata carries T-value counts.

The display name shown in the pipeline is resolved at load time from the detected metadata, for example "PAL TBC Composite" or "NTSC TBC YC".

## Video systems

PAL, NTSC and PAL-M from the metadata. SECAM comes from the project: in a SECAM project a 625-line TBC is read as SECAM, and a 525-line one is refused. A PAL, NTSC or PAL-M project refuses a TBC that is labelled SECAM.

## Status Indicator

The coloured dot in the top-right corner of the node shows its configuration status.

| Colour | Meaning |
|--------|---------|
| Green | Fully configured and ready to run. The TBC file and its metadata are present and readable. |
| Yellow | The TBC file is present but its metadata sidecar is missing or unreadable. The stage cannot run until the metadata is available. |
| Red | Not configured. No file path is set, or the configured path does not point to an accessible TBC file. |

Parameters can be set via **Edit Parameters...** in the node context menu. Some stages also provide interactive stage tools (listed under **Tools** above) that set parameters directly from within the tool.
