# Closed Caption Sink

Extracts one EIA-608 service from NTSC Line 21 — or the Extended Data Service, or every service at once — and writes it as Scenarist SCC, SubRip subtitles, plain text or an HTML transcript. Use this stage in parallel with the TBC Sink stage when archiving captioned NTSC LaserDiscs.

## When to use

Add this sink when you are processing an NTSC LaserDisc that carries Line 21 closed captions and you want to preserve or inspect the caption data. SCC is the archival format and loads into caption-authoring tools; SRT plays in any modern media player; plain text is for reading; HTML keeps the column layout, which is what makes a text service such as a listings or scores page readable.

## What it does

For each frame in the pipeline, the stage reads the byte pair Line 21 carries on each field, through the host's closed-caption observer — the reading the rest of decode-orc shows — selects the pairs belonging to the chosen service, and writes them in the chosen format.

A line is read only when it carries Line 21's waveform. The observer finds the clock run-in — seven cycles of a sine at the bit rate, 32 times the line rate, anywhere from 7 to 12 µs after 0H, which must account for most of the line's variance where the run-in lies — takes the bit timing from the run-in's phase and the slicing level from its midpoint, and finds the two 0 start bits and the 1 start bit where the run-in puts them; a weak run-in, half buried by a dropout, is read only when every data bit stands clear of the slicing level. The last data bit ends where captures cut the line short (vbi_source writes a crop up to 61.0 µs after 0H; a BT.601 picture ends at 62.4 µs), so it is read from the early part of its cell. Each byte's parity is then checked as odd over all eight bits. A line of noise, picture, a test signal or another service's data is not read, however it slices.

The stage takes a byte pair only when both bytes' parity held — or the first byte's did and it is a character, which is kept alone, as a receiver displays the character it did receive. A byte that has no function on its field is ignored alone and its partner treated normally [47 CFR 15.119(i)(1)]: a first byte 00h–0Fh on the first field (on the second it is the Extended Data Service's), and a second byte 01h–1Fh after a character or a null — a text service can end a row's last character with 01h, and refusing the pair would lose the character. The pair must then be a control code or characters EIA-608 defines for its field, and its field must carry Line 21 data around it: at least three pairs with good parity within thirty frames either side, as a captioned field carries the run-in and a pair on every field and a decoder enables its display only on a run of valid data. Without these checks, a recording whose Line 21 carries no data at all yields stray characters, and stray control codes elsewhere can switch a caption service into a text service for thousands of characters; with them, nearly every pair the stage takes is one independent line 21 decoders agree on, and of the pairs they agree on it misses almost none that EIA-608 defines. The run-in is searched for from 7 µs after 0H, so a caption whose run-in starts early is still found.

Which stored field is television field 1 is decided from the whole run: field 2 spells the miscellaneous control codes 15h and 1Dh where field 1 spells them 14h and 1Ch, and only field 2 carries the Extended Data Service. A capture whose first stored field is television field 2 — as some card dumps and crops are — has its fields read the other way round, so that its CC1 comes out as CC1, and the report says so. To decide this the run is read through before anything is written, keeping eight bytes for each line that carried a pair, and twelve where both its parities held.

A recording whose time base slipped a line carries its captions on line 22 or line 20 instead of line 21 — throughout, or on lines 20, 21 and 22 by turns. Where line 21 carried nothing, the pair read on the line next to it (22 first, then 20; see the Closed Caption Observer) is taken if, over the run, that line reads as a caption line does: twenty fields or more, three quarters of them with both parities good — the measure cc_decoder uses — and eight control codes among them, which a caption stream carries and a test signal slicing into one fixed pair does not — and only where line 21 carried nothing for fifteen frames either side, where the caption line has moved rather than lost a field: on a card dump, line 20 can read a pair on fields where line 21 lost one amid its own, and taking those makes the captions worse. Its pairs are then taken as line 21's are, by the same rules, and count towards the field order and the run of data around each pair. The report says how many came from each line. A recording whose line 21 carries its captions throughout reads exactly as it did.

The second field also carries the **Extended Data Service** (XDS): packets naming the station, the network, the programme and its start, the time of day and the time zone, each closed by a checksum. Its pairs are separated from the second field's caption and text services before they are demultiplexed, and assembled into packets; a packet whose checksum fails is dropped. Each value is written as CTA-608-E §9.5 codes it: the programme's length and time in show (`01:00, 00:59:05 elapsed`), its type's keywords (`Entertainment, Drama`), its content advisory under whichever of the four rating systems it uses (`TV-PG (violence, adult language)`, `MPA PG-13`, `Canadian English 14+`, `Canadian French 13 ans +`), its audio and caption services, its copy control, the channel's tape delay and transmission signal identifier, and the end of a programme; private data, and the types and rating systems the standard reserves, stay in hexadecimal.

Line 21 does not carry one caption stream but four on each field, multiplexed into the same two bytes per field: **CC1** and **CC2** (captions) and **TEXT1** and **TEXT2** (pages of text such as schedules, scores or station information) on the first, **CC3**, **CC4**, **TEXT3** and **TEXT4** on the second. Which service a byte pair belongs to is decided by the control codes that came before it: the data channel by the last control code's channel bit, captioning or text by the last of the codes that select one. End of Caption, Erase Displayed Memory and Erase Non-Displayed Memory act on the channel's caption memories even in the midst of a text stream [CTA-608-E §7.7, C.16]: routed to the text service, as they were, an End of Caption sent between two rows of text never put its caption up, and an erasure cleared the text page instead of the caption. The text stream keeps the channel until a code selects a caption style (RCL, RU2, RU3, RU4, RDC); CTA-608-E has End of Caption end it too, but a text service can send EDM, EOC, EDM inside its stream and resume with Resume Text Display, and where that was lost the rows after it are still text, not captions written over one another. Exported without demultiplexing, a recording that used more than one service produces garbled output — a caption running through a page of listings. This is what the `service` parameter is for.

## Parameters

### output_path (string)
Path to the closed-caption output file. Required. Conventionally `.scc`, `.srt`, `.txt` or `.html` to match the format. With the service `All`, the folder the services' files are written into (made if it is missing).

### service (string)
Which of the services multiplexed onto Line 21 to export. Values: `CC1` (the primary caption service, and what most recordings use), `CC2` (a second caption service, often a translation), `TEXT1` and `TEXT2` (text services), their second-field counterparts `CC3`, `CC4`, `TEXT3` and `TEXT4`, `XDS`, the Extended Data Service, which is exported as `Plain Text` or `HTML` only: a listing of each packet whose value changed, with when it arrived (`00:01:12:03  Channel: network name: PBS`), and `All`. Default: `CC1`.

`All` exports every service in one pass over the recording, into the folder `output_path` names: `CC1.srt` to `CC4.srt` as SubRip, `TEXT1.txt` to `TEXT4.txt` and `XDS.txt` as plain text, each exactly what the export of that service alone writes, and a file only for each service that carried anything; the report, when asked for, is `line21.report.txt` there. The `format` parameter does not apply to it. Reading a recording once instead of once a service is what makes an archive of hour-long tapes practical: a recording carrying five services takes one pass instead of five.

To export some services and not others, add a Closed Caption Sink for each with its own output path.

### format (string)
Export format. Default: `Scenarist SCC`.

| Value | Output |
|-------|--------|
| `Scenarist SCC` | Scenarist SCC V1.0: `HH:MM:SS:FF` timecodes and the selected service's byte pairs exactly as transmitted, channel bits and the duplicate copy of each control code included. Consumers of an SCC file de-duplicate for themselves. |
| `SubRip SRT` | Numbered cues with `HH:MM:SS,mmm` times |
| `Plain Text` | Each caption under a `[HH:MM:SS:FF]` timestamp |
| `HTML` | A monospaced transcript, each caption in a `<pre>` block beside its timestamp |

In the three decoded formats the rows of the caption display stay on separate lines and keep their indent, so a text service's columns still line up. A mid-row code — the colour or italics change in the middle of a row — takes a column as a space does, and a tab offset moves along one to three columns [CTA-608-E §7.4, Table 52], so a word put in italics stays a word apart ("THE ENTERPRISE IS", not "THEENTERPRISEIS"). Preamble address codes are read as CTA-608-E Table 53 lays them out: the codes beginning 13h address rows 12 and 13, not 13 and 14, so a two-line caption on rows 13 and 14 keeps its first line, which its second used to overwrite; and data channel 2's, spelled with 08h set in the first byte, place CC2 and TEXT2 as channel 1's place CC1 and TEXT1, where they were ignored. Each style is decoded as 47 CFR 15.119(f) and CTA-608-E describe it:

* **Roll-up**: a cue is the window RU2, RU3 or RU4 chose — the base row and the one, two or three rows above it. A carriage return erases the window's top row and scrolls the rest up, a preamble address code naming another base row moves the window there intact (with no room above it for the window, the depth wins [CTA-608-E C.4]), a shallower window erases the rows it turns off, and selecting roll-up erases a pop-on or paint-on caption from both memories [47 CFR 15.119(f)(1)]. Scrolling the whole display instead kept every row ever written, so each cue carried the caption's earlier rows too, and a roll-up stream came out at more than twice its words.
* **Paint-on**: a cue is the displayed memory as it is painted, its rows placed by their preamble address codes [47 CFR 15.119(f)(3)], and Resume Direct Captioning, which an encoder sends before each burst [CTA-608-E B.8.2], continues the same cue. Built character by character, a two-row caption runs its rows together ("WE WERE DRINKINGSO MUCH JUICE").
* **Pop-on**: End of Caption swaps the two memories and erases neither, in any style, and selects pop-on [47 CFR 15.119(f), CTA-608-E C.10, C.11]. The decoder remembers one caption cursor, which neither the swap nor an erasure moves [CTA-608-E C.15]: a stream can come back from a commercial with an End of Caption, a few characters and only then a preamble address code for the next row, and a cursor reset to the start of the bottom row would put those characters where that row overwrites them.
* **Text**: a text service is a scrolling page rather than a caption window: a preamble address code moves the cursor to its indent on the current row and leaves the row alone [CTA-608-E §7.4]. A text service can send every line as a carriage return and a code addressing row 1; followed as an address, that wrote each line over the one before it ("DAY AND TIMES.CAL LISTING"). Resume Text Display carries the service on from the same cursor position [CTA-608-E §7.4]: a row a caption interrupts is sent again from its start after Resume Text Display and a preamble address code back to its indent [CTA-608-E D.3], and is one line of the output, written over itself. It used to come out twice, the part before the interruption first. Where the second sending reads otherwise than the first — damaged, or with the carriage return between two rows lost — what the row read before was on screen too and stays a line of its own.

The decoded formats are UTF-8. EIA-608's basic character set is ASCII but in ten places — 2Ah is "á", 5Ch "é", 5Eh "í", 5Fh "ó", 60h "ú", 7Bh "ç", 7Ch "÷", 7Dh "Ñ", 7Eh "ñ" and 7Fh the solid block [CTA-608-E Table 50] — and the two-byte characters are written as what they are: the special characters, the music note (♪) that marks a song's words, ®, °, ½, ¿, ™, ¢, £ and the accented letters the basic set lacks [CTA-608-E Table 49], and the extended characters, each of which takes the place of the standard character sent before it for receivers without them ("u" then "ü" reads "ü") [CTA-608-E §6.4.2].

### write_report (boolean)
Write a report of everything Line 21 carried beside the output, named after it with `.report.txt` (`captions.scc` gives `captions.scc.report.txt`; with the service `All`, `line21.report.txt` in the folder). Off by default; the same report always goes to the log. Whatever service the export is of, the report counts both fields: how many lines carried Line 21 data, how many pairs were taken and how many of them were not null padding, how many were refused as no code EIA-608 defines or as standing alone, and the characters of each of the eight services; whether the capture's fields were read the other way round; the XDS packets, each type with the values it carried (the station's call letters and network, the programmes' names and starts, the time of day it ran over, in UTC, and the time zone); and the ATVEF triggers on TEXT2 — the `<url>[attribute]...[checksum]` strings ATVEF 1.1's Transport A sends there. A trigger is counted only when it is well formed — an `http:`, `https:` or `lid:` URL of the characters a URL may hold, then attributes — and its checksum, which CTA-608-E §7.12 requires, holds; well-formed strings whose checksum is missing or fails are counted apart.

## Notes

What the stage takes is what a pair's own line shows: a character damaged by noise but whose parity still holds (two bit errors) passes, as it does for any receiver. A pair whose first byte's parity failed is dropped whole, since it may have been a control code; an encoder sends each control code twice so that its second copy stands in [CTA-608-E §D.2]. A receiver built to the FCC's rule shows a solid block for a character whose parity failed [47 CFR 15.119(j)(1)], as cc_decoder does; on recordings most such blocks stand where no other decoder can read a character either — damaged null padding, or lines nothing can read — so a damaged character is left out instead.

The video sink's embedded subtitles take their pairs by the same rules, field order included, through one shared helper (`orc/support/eia608_line21_pairs.h`), and decode them with the same decoder. The GUI's caption preview applies them too, except that a pair needs Line 21 data around it: that rule looks at frames after the one the preview shows, so a lone line of noise that reads as a defined code can still reach the preview.

CC data must be present in the source capture — this stage cannot synthesise captions. It handles NTSC Line 21 only; PAL sources do not carry Line 21 CC data. Do not use a Mask Line transform to blank line 21 before this stage, as that will destroy the caption payload. If the source fields contain no CC data the output file will be empty but the stage will not abort.

## Status Indicator

The coloured dot in the top-right corner of the node shows its configuration status.

| Colour | Meaning |
|--------|---------|
| Green | Fully configured and ready to run. All required parameters are set. |
| Yellow | Partially configured. The stage can run but will use default or reduced behaviour — for example, pass-through mode or console-only output. Review the parameters for optional settings. |
| Red | Not configured. One or more required parameters are missing and the stage cannot run. |

Parameters can be set via **Edit Parameters...** in the node context menu. Some stages also provide interactive stage tools (listed under **Tools** above) that set parameters directly from within the tool.
