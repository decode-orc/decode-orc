# NABTS Sink

Recovers North American Basic Teletext (NABTS) data lines from the VBI of a 525-line source, writes the recovered packets as a flat stream, and presents the records it found — decoded as pages — in a record viewer.

NABTS is **ITU-R BT.653 System C**, specified by [CEA-516](https://www.cta.tech/) (formerly EIA-516). It is the service the US networks carried in the 1980s — CBS ExtraVision and NBC Teletext among them — at 5.727272 Mbit/s in 33-byte data packets, written here as `.t33`. Its presentation layer is **NAPLPS** (ANSI X3.110-1983, also CSA T500-1983 and ITU-T T.101 Data Syntax III): a page is not a grid of characters but a drawing program, so a record can contain lines, arcs, polygons and redefinable characters as well as text.

It is **not** World System Teletext. On a 525-line capture the two services share the clock run-in, the bit rate, the VBI lines and the data levels, and are told apart by the framing code alone: `0xE7` for NABTS against `0xE4` for WST (the `27` encoder manuals give, its bits taken least significant first). The encoders of the day made the code a setting — Norpak's TES inserters call it the NABTS "byte sync", default E7, "not usually modified" — and NABTS services use E7; other framing codes found on NABTS's physical layer belong to other services and carry no NABTS prefix at all. If a recording carries WST rather than NABTS, use the **Teletext Sink** instead, which writes 34-byte `.t34` packets. A stage pointed at the wrong service recovers nothing rather than recovering nonsense.

## When to use

Add this sink when an NTSC or PAL-M source carries NABTS you want to preserve or inspect. The recovered packet stream is the product: it holds the transmitted packets exactly as broadcast, which is what any other data-group and record decoder needs. The record catalogue rides along with it, which is why this is a sink rather than an analysis sink; leaving `output_path` empty makes the catalogue the only thing the run produces, and that is supported.

Expected recovery quality depends on the source's luma bandwidth at the data rate:

* **Broadcast-quality captures and direct CVBS** carry the full spectrum; recovery is expected to perform like a hardware decoder.
* **Consumer VHS** truncates the upper half of it, causing heavy intersymbol interference. Threshold slicing cannot recover anything at all from such a recording — the clock run-in is the first thing the tape loses — so the stage carries a second bit detector for this case; see `detector` below.

How well a *tape* does depends sharply on its recording speed, and NABTS is far less forgiving of a marginal recording than World System Teletext is. See **What a marginal tape looks like** below before concluding that a disappointing result is a fault.

## What it does

Trigger the node and it makes one linear pass over the whole frame range, carrying the recovery up through all four layers CEA-516 defines.

**Packets (§3).** For each frame it probes the candidate VBI lines of both fields for a data line and extracts the 33 packet bytes. Recovered packets are written to the output file in strictly temporal order — frame, then field 1 and field 2, then ascending line — exactly as a receiver would have seen them broadcast, which is the order a data group has to be reassembled in.

The output is a flat, headerless sequence of whole 33-byte packets in **transmission coding**: the Hamming 8/4 protection on the five prefix bytes and the odd parity on the data block are preserved, so a consumer decodes the stream exactly as it would a live transmission. Nothing is corrected in the file.

A line yields a packet only when its five-byte prefix survives Hamming 8/4 correction. The prefix is the three packet address bytes, the continuity index and the packet structure byte (CEA-516 §3.2.1), all error-protected under the same code. Requiring all five suppresses false locks on noise — random bytes survive correction about one time in eighteen, and arrive with all five exactly as codewords about once in a million — and a packet whose prefix is unrecoverable could not be placed in a data group anyway. A packet structure byte that describes a synchronizing packet with no data block (§3.4, §4.2.1: the group header it opens a group with has nowhere to go) fails the prefix as well; that is what a test signal repeating one byte that happens to be a codeword decodes as. The threshold detector also takes the framing code only exactly as CEA-516 §2.2.3 defines it: the framing code is the only thing that separates NABTS from the 525-line World System Teletext service, so tolerating an error in it would both raise the false-positive rate on noise and weaken that separation. (The MLSE detector reads the code back rather than searching for it, and allows the one wrong bit §2.2.3 provides for; see `detector`.)

**Data groups (§4).** Packets are reassembled into data groups per data channel, since §3.2.3 makes the packet address the channel number and a service may interleave several. A group opens on a synchronizing packet and runs until its length is satisfied, with the continuity index catching a packet that went missing in between. The index is believed only where the loss it claims could have happened: see **Continuity indices that could not be true** below.

A group that ends before its length is satisfied — the next synchronizing packet on its channel arrives first, or the recording ends — lost its last packets, the commonest loss of all and the one no later continuity index is there to show. Its header says how many blocks there were (§4.2.5), so the group is kept at that length, the blocks it never received held open as a hole like any other loss: its bytes stay at the offsets the record gave them, and in a linked record (§5.2.6) every later link stays where it belongs instead of moving a block earlier. A packet structure byte is Hamming 8/4 like the rest of the prefix, and a packet whose byte names a different suffix from the rest of its group (§3.4) had it misread; its block is read at the width of the group's synchronizing packet instead of moving every byte after it by one or two, and nothing vouches for it, since its suffix check was made over a layout the misread byte named. Both keep the bytes after a loss where they belong, so the copies of a page vote on the bytes they share rather than on bytes displaced against each other.

**Headers misread.** A burst can misread the packet structure byte of a data packet as synchronizing (§3.2.5 b2), and the packet then offers its first eight data bytes as a group header, which Hamming 8/4 refuses. Where the group open on its channel expects exactly that packet's continuity index next, the packet is that group's next block and is taken into it, rather than refused and the block lost; the report's **Misreads** line counts them. On one badly damaged tape a third of the refused headers were such packets. A group type read on a teletext channel — one that has carried a type-zero group whose type arrived as a codeword — as some other type whose byte had to be corrected is a type zero a burst moved, and is read as zero: on damaged tapes hundreds of groups arrived typed 0xB that way, nearly all with a record header that decodes, and would otherwise have been dropped as another application's data. A type that arrived as a codeword is believed.

**Groups whose first packet was lost.** A group's synchronizing packet carries its group header and its record header, and a recording that loses a line in every field loses it whenever a group happens to start on that line. The rest of the group then arrives on a channel with no group open, and is collected as a *loose run*: the packets in order, with a hole held open where the continuity index says a packet went missing, ended by the next group on the channel, by a gap of more than two packets (past which the packets are as likely the next group's, whose start went too), or at a group's length. After the vote, each run is set against the listed records of its channel at the alignments their shared six-byte stretches suggest, and where nearly all the bytes both hold passing their parity agree (85 % of at least 40), the run is a copy of that record. Its bytes then fill the record's holes — the bytes no copy delivered — and never a byte the vote settled: a recording that loses one line of three loses blocks 2, 5, 8 and so on of every group that starts on the first line, and a group whose start fell on the lost line kept exactly those. A run no listed record holds is part of a page none of its copies named: runs are matched to one another the same way, those a run agrees with being one page, and a page of two or more runs — or one clean enough to stand alone, nine bytes in ten passing their parity — is voted from them and listed after the named records as **CCC/LOSTn**, its channel known and its address and version not, marked **header lost**. Its head, the record header and the first bytes of its presentation code, went with the synchronizing packet and is held as lost; where the first shift its code holds is SI, the bytes before it were picture description, and the page starts with the SO they followed, supplied and marked as not received. A page whose code reads, byte pair by byte pair, much worse than the service's own records (the channel's dialect, learned from them) is fragments of damaged copies and is not listed. On one recording that lost the start of a third of its groups, three dozen news, sports and market pages that never once arrived with their header are listed this way. The report's **Salvage** line says how many runs were found in listed records, how many bytes they filled, and how many pages were listed and refused; `export_records` writes a salvaged page as `mydata.t33.000-LOST1-v0.rec`. The runs placed nowhere — a copy of no listed record and part of no listed page, or on a channel no record was named on — are received bytes all the same, and `export_records` writes them as they arrived to `mydata.t33.fragments.txt`: a block a run, with its channel, the frame it ended in and its packets, then its bytes as characters, the shifts and escape by name ({SO}, {SI}, {ESC}), `~` for a byte failing its parity and `_` for one of a lost packet.

**Records (§5, §7).** A group of type zero carries a teletext record: a Hamming 8/4 header giving the record type, its address and its classification flags, then the record's data. A record can be transmitted as a linked series (§5.2.6), and the series is joined back into one message in link order — which may arrive out of order, because a recording that starts part way through a carousel sees the middle of a series before its beginning. A series is joined once every record from its first to its last has arrived. The link order is Hamming 8/4 like the rest of the header, and damage can resolve it silently into another number, so a record numbered past the last record of its series is no part of it and is set aside, and a linked record that claims to be both the first and the last (a record that is a message on its own is sent unlinked) is a later record misread as the first and is set aside too. Counted in, such a record would complete a series still missing its first record, and the message would come out with its records out of order — the second before the first, or the second twice — and be listed as a page of its own. A series that still lacks its first record when the recording ends, or when it is evicted at the open-series limit, is not delivered at all: §5.2.6 gives a message its first record's classification, and neither receiver of the day shows a series it has not taken from its first record on (the TU-2000x checks each record's link order against the one it expects, the TTX 650 filters on the link nibbles). Such a series is records whose headers were misread — an address or a link order read wrong — and listed, it would show a fragment as a page, or stand in for a page with a fragment longer than the page's own copies. The report's **Unheaded** line counts them. §5.2.1 makes channel, record address and version the identity of a record, and that is what the catalogue is keyed on — with one refinement. An identity can carry more than one record over a recording: a carousel can give each page in turn the next of the sixteen versions §5.2.7.2 allows and use the versions again when it comes round with new pages, and a page can be replaced without its version moving. So each copy that arrives is compared with the contents already held under its identity — with every copy each holds for its vote, not only the one it keeps, which is the longest rather than the best — on the bytes both have that pass their parity and at the few bytes' slip a misread header causes (see the notes on combining copies below). A copy that agrees with one of them on at least half of those bytes is a copy of it. Where no one slip lines the two up, they are compared again window by window, two blocks at a time each at its own slip, and seven bytes in ten agreeing that way make the copy the content's too: a packet lost without the continuity index showing it moves every byte after it by a block, further than any header misreading does. A copy that agrees with none, or that arrived intact at a length that differs from an intact copy of the content, is a record of its own. Once the last copy is in, a content that the copies held for an earlier one show to be the same page is joined to it, since a copy damaged where the first copies were not can only be told for what it is once more copies are in — and the windows are then allowed a slip of three blocks: a group given holes for blocks it never lost — a continuity index misread where lines went by — puts every byte after them two or three blocks late, and such a copy would otherwise be listed as a page of its own. The windows are laid over the content held and, failing that, over the copy: a copy that kept only a few dozen of its bytes lends those few bytes to several of the content's windows at slips that do not line them up, where laid over the copy each of its bytes is read once.

Two pages built on one template are the exception to all of that agreement. A carousel's ratings, scores or headline pages share every byte of their layout, which can be most of the record — two such pages can agree on three quarters of the bytes both arrived with — and voted into one record they come out a per-byte blend, rows of one page among rows of the other. What tells two such pages apart is what each carries that the other does not, and damage does not do that: a stretch the recording garbled fails parity in every other byte, the commonest misreading — two neighbouring bits of one byte — passes parity but leaves single bytes wrong, and a lost or misplaced block moves bytes without changing them. So two copies, or two contents, that agree are still two pages where each holds against the other either thirty-two bytes or more, in runs of four or more, where both bytes pass their parity and differ with no more than two bytes failing parity within fourteen of the run, or six bytes or more — and eight in a hundred of the bytes the suffix check vouched for in both — where the two vouched bytes differ (the check passes two misread bits down one column, and a block the MLSE detector read again under its check can pass it with a byte still wrong, so a few vouched bytes in a hundred differ between copies of one page); in either case only bytes no move explains, the copy's bytes around them found nowhere in the other within 96 of them, and each way round, since a copy cut short or moved carries nothing its page does not. Damaged copies of one page agree on nearly all their bytes and seldom fall below half, while two different pages under one identity agree on few, so the test parts pages a revision or a carousel put under one identity and leaves a damaged copy with its own page; two copies that differ by only a few dozen bytes, or by a block moved, are the same page revised and stay together. Each content is catalogued, exported and listed as a record of its own, numbered after the identity in the order they first arrived — `000/100 v4` and `000/100 v4 (2)` in the list, `out.t33.000-100-v4.rec` and `out.t33.000-100-v4-2.rec` on disk. Voted into one record, two pages under one identity would come out a per-byte blend of both: one page's text in the other's lettering, or a drawing with another page's shapes over it.

Length tells two contents apart only where both arrived intact — every block of every group vouched for by its check (§3.4) — since only then is a copy known to be as long as its record. A block the MLSE detector read again under its check (see `detector`) does not count towards that: it passes the check because it was read to, and a copy that lost a packet without a gap in its continuity index — one block short — would pass for intact once its other blocks are read so, and be listed as a page of its own. Its bytes are still vouched for in the vote. A block the detector read wide (see `detector`) is one read under its check as well, and the bytes the wide reading changed are no evidence here either way: a reading taken because more of the packet's checks pass under it passes them whether it is right or not, so a copy whose damaged stretch it read wrongly differs from its page in bytes that pass parity, as a copy of another page does. They are compared as what they arrived as — bytes failing their parity; compared as bytes that pass their parity, they would join copies of different pages and split copies of one. A copy that arrived complete, every link of a linked series, can still be short of it: the group that carried its last link may have lost its tail (see **Data groups**), and a misread group header declares a block too many or too few. Judged by their length, complete copies would be split from their own page — a page coming out as one record for each length its copies arrived at — so they are told apart by what they carry instead, and every pair of contents known to differ is still listed apart. What is left is pages that really changed: a carousel with more pages than versions, editions of a magazine, pages revised while the recording ran, and text feeds as messages were added.

**Captions (§7.3.10).** The caption service is the one exception to that key. §7.3.10.1 has captioning sent as records at one address that change version each time the caption changes, each repeated a few times to aid error recovery (§7.1.3), and the version is one Hamming 8/4 digit (§5.2.7.13): over a recording the sixteen versions are used again and again by captions that share nothing but the number, a captioned programme carrying hundreds or thousands of captions under them. So captions are not catalogued. They are kept in the order they arrived: a caption is a run of consecutive arrivals at one channel and address carrying one version, and the next arrival there with another version starts the next caption. Only a caption's own copies are combined with each other (see the notes on combining copies below), and a caption is dated by the first frame of its run, which is when a receiver would first have shown it.

An arrival belongs to the caption service when it carries the Caption Flag of §5.2.7.3 and its header arrived as transmitted, names a non-cyclic presentation record — the record type §5.2.2.3 says captioning is sent as — or comes from an address the caption service is already using. A cyclic page elsewhere whose header had to be corrected into shape and reads the flag is a page with a misread bit, and it stays in the catalogue, where its flags are voted from its appearances (see **Addresses the recording named but the service never sent**). The converse damage is caught too: a non-cyclic arrival whose header was corrected, at an address the caption service is already using, is taken as a caption even when its flag byte reads clear.

**Other services (§4.2.2).** A group of any other type is not teletext. §4.2.2 reserves type 15 for the service provider's private use and every other non-zero type for standardization that never came, so what such a group carries is in a format the standard does not describe. It is listed as it arrived: a channel whose groups arrived with their channel and header received as transmitted — Hamming 8/4 codewords, not corrected into them — is named in the viewer's notices and in the report's **Not teletext** lines, with its group type and how many groups it carried, and its groups are an item of the viewer's **Other services**, one a channel and type: each group under a line giving its channel, the frame it ended on, its type and group continuity, in the order received; a group that reads as seven-bit text as its text, any other as a dump of its bytes, sixteen to a line with the characters they read as (`??` a byte lost with its packet), and a group whose every byte is a Hamming 8/4 codeword, padded out with NUL, also as the digits those codewords carry, as a control message is sent. Noise corrects into a non-zero type often, by the hundred on a poor transfer, but never arrives clean, so a named channel is a service the recording really carries. A recording carrying nothing else — a single channel of type-15 groups, say, whose data is text in a code of its own — lists those groups and says it carries no teletext, rather than looking as though the node never ran. A provider that sent presentation records under a reserved type is read all the same: a group of any type whose header is a presentation header, its identity received as transmitted, and whose data opens with SO (0/14, the shift into the NAPLPS graphics set a page opens with) is a record, and so are the later groups of the linked series it opens.

**Services that are not teletext at all.** NABTS is a transport, and not everything a recording carries on it comes in data groups. The pass keeps a census of every packet address that arrived as transmitted and, at the end, names the ones that carried one of four other kinds of service, each recognised by a test teletext does not pass:

- an **FEC datacast**: packets with the two-byte suffix (§3.4 PS b8,b6 = 1,0) whose suffix is the Reed-Solomon row code of RFC 2728 Appendix A — Norpak's FEC, over GF(2^8) modulo x^8+x^4+x^3+x^2+1 with roots alpha and alpha^3 for alpha = 00011101, so g(x) = x^2 + 146x + 157 — on at least half of them, with how its bundles lay out data rows and check rows (the packets whose suffix is all 28 bytes): RFC 2728's own sixteen-packet bundles with the checks at continuity indices 14 and 15, or so many data rows to each check row or pair of check rows. A teletext service's two-byte suffix is a longitudinal check, and passes the row code only by chance, on a few packets in ten thousand. Consecutive addresses carrying the same layout within one block of sixteen are named together, so a family of sixteen datacast addresses is one line;
- **idle fill**: an address whose packets, the ones the suffix check does not call damaged, are at most 256 distinct contents repeated, each byte of them the one before it shifted a place — the bit-error-rate test (BERT) pattern an encoder sends when it has nothing else to send, which the Ross Video (Norpak) TES3/TES5 encoders send on address F00 (their manual, Iss. 02 p. 10-3). In such fill nearly every pair of unequal neighbouring bytes steps that way; on any other address only a few in a hundred do;
- a **test sequence**: packets each a stretch of one short linear-feedback shift register sequence, at most 32 stages, judged by Berlekamp-Massey over the 224 bits after the prefix, with its polynomial — x^11 + x^9 + 1, say, ITU-T O.150's 2^11 - 1 sequence. A run of one byte repeated is not one;
- **clock packets**: Hamming 8/4 bytes carrying a Unix time of day that advances by no more than ten minutes from one time packet to the next, with the span it covered in UTC and the name it carries. A clock sent on two addresses at once is named once.
- **text in the provider's own data groups**: groups of a type §4.2.2 reserves, whose channel and header arrived as transmitted, and at least three quarters of whose received bytes (and at least sixteen) are seven-bit characters with odd parity — printable, or a line break or tab. A provider could send teletype traffic that way beside its pages: news rundowns, wire stories, feed notices, memos. With `write_report` set, the text goes beside the report as `mydata.t33.other.txt` with every other group of a reserved type, each listed as the viewer lists it (see **Other services** above) — a byte of text that is not text shown as `.`, bytes lost with their packet as `[...]`.

They are listed in the report under **Other services (not teletext)** — the text's file under **Private text** — and in the viewer's notices, each saying where what it carried is listed: a datacast by its addresses, with the files and services read out of it, and a provider's own data with the other services'. A clock names the span of time it covered, which dates the recording to the second.

**Datacasts decoded.** An FEC datacast is decoded as RFC 2728 §3.3 and its Appendix A lay the code out, with the bundle layout read from the stream: the commonest run of data rows that a check row closes is a bundle's data, and what follows it — two check rows (RFC 2728's own layout), or a skipped continuity index and one check row (a service that sends only the second of the two), or the reverse — is its check part. Whether those check rows close the data before them or open the data after them is decided by the column code itself: the reading under which its columns hold. Rows are placed by their continuity index and re-anchored at every check row, so a run of lost packets longer than the index counts costs only the bundles it fell in. Each row is corrected in one byte where its two sums point at one (Appendix A 12.4.3), then each column, with up to two rows that are missing or still fail their row code replaced from the column code (12.4.4) — which is what brings a lost packet back; a check row a service never sends is one of the two, and a bundle with one row missing checks its own replacement on the other sum. Where that other sum fails, a row of the bundle is wrong though its own code holds: a row two bytes wrong can be changed by its code into the wrong codeword. Such a row is found among those its code changed — rebuilt from the columns, it and the missing row put aside, it alone lies within two bytes of the row as it arrived — and put right; where no row or more than one answers so, nothing is rebuilt from the bundle. A bundle holding more erasures than the column code takes alone — two rows or more failing their own code, besides at most one row missing (a service sending one check row of the two always misses the other) — is put right by the column code and the rows' own codes together: the columns whose two sums do not agree say where the failing rows are wrong, and each way of giving those columns to the failing rows, every failing row two at least, is a reading, its erasures filled from the columns and the rows' codes in turn. A reading holds where every code then holds — the check row never sent is a row of the row code like the rest, so rebuilt from the columns it checks the reading — and the bundle is put right only where exactly one does. With two rows missing every column's sums go to filling them and what the rows' codes add follows from the columns' (a product code's checks are not all independent), so a row lost beside a failing one stays as it is. The report counts the rows so rebuilt with those the column code rebuilt. The payload is every data row in order with its filler removed (RFC 2728 §3.2: 0x15, then as many 0xEA as fill the block), each row keeping the frame of the recording it arrived in. A row a channel flags as not full of data (PS b4) ends in filler's bytes; a channel whose flagged rows end in them no more often than rows full of data do by chance sets the flag on every row it sends, and its rows are taken whole — read as filler, a row that happens to end in 0x15 would lose its last byte. A channel that sends its data in no data groups and with no row code at all — a stream of blocks, with almost no synchronizing packets — is written out too, as a *raw stream*: its blocks in the order the continuity index gives them. Only packets whose address arrived as transmitted count towards one, and a channel whose continuity index says more than three packets were lost for every one received is no stream: a stream's index counts its packets, while the index of another service's line read as NABTS falls anywhere and that of a packet sent over and over never moves. What a payload means is its service's own (programme guides, weather file transfers, logs, encrypted feeds), so the report says what it can without knowing the service: whether its SLIP frames carry RFC 2728's CRC-32 (an IP datacast's every frame does; none of the recordings measured carries IP), how much of it is text, and which file formats' signatures it holds. The report lists one line a channel under **Datacasts decoded**, and with `export_records` each payload is written beside the stream as `mydata.t33.datacast-242.bin`, with the text it holds — every run of forty printable characters or more, a run to a line — as `mydata.t33.datacast-242.txt`.

**Files the datacasts carried.** Three framings of files were found on the recordings, and a payload in any of them yields its files, each listed in the viewer after the datacasts and written with `export_records` beside the stream as `mydata.t33.datacast-<channel>.<name>-<time>.<extension>` — a framed service's in the website mirror instead (see **Website mirror** below):

- A **file transfer**: messages of the byte 0xFF, a length, a kind and that many bytes. Chunk messages carry a four-byte file number — the Unix time the file was queued, which dates it — a two-byte chunk number and 128 bytes of the file; each chunk is sent twice and files interleave. A file is its chunks in order, a chunk that never arrived a hole of zeros the report counts. A message across a row the recording lost is not believed, since its bytes past the gap belong to the next one.
- A **file carousel**: each row holds 25 bytes and their sum; a directory entry gives each file's 8.3 name, time and length, and its data follows in numbered blocks of 392 bytes, one bundle each. The carousel sends every file over and over, so each block is voted from its copies byte by byte, with the rows the recording lost held open so a copy's bytes stay where they belong, and a block header is believed only at the start of a row and giving the length its place in the file says. The directory entry also gives the sum of the file's bytes, and a whole file is checked against it. The carousels measured hid their text files behind a byte substitution keyed by the sum of the file's name plus an offset each carousel keeps: the offset is the one under which the carousel's whole files read through the substitution add up to the sums their entries give. A file that reads as text through it is listed read, any other kept as sent.
- A **framed service**: a service that spreads its data over a family of sixteen addresses, each frame the sixteen data rows of a bundle — a header row, then the object bytes after it — with every byte sent XORed with a fixed pad, the same for every frame of every service of the kind on the recordings: what a frame of zeros arrives as. Under the pad a frame's header counts the frame (bytes 5-6, one more than the frame sent before it on any address of the family), names its service (bytes 9-12), and says which object the frame is part of (13-14) and where in it its bytes go (15-18); bytes 7-8 mark the frame that ends an object. The frames of all the family's addresses are put back in the order of their counts, followed across a wrap, and counts missing are frames sent and not read. A frame whose header row arrived is read even where others of its rows did not, those rows left out of it. A frame is looked for only where a bundle starts, a service's frames are taken from its block of sixteen addresses — a header row on another came on a misread address — and a name only scattered frames bear is a misread one. An object is a file: its first frame opens with the object's own header — its number, its time (Unix seconds), its size and its name — and the file's bytes follow. A service sends an object over and over and may change it between passes, so passes that read alike are one version and each version is a file of its own, voted row by row from its copies; versions of a container that, voted together, unpack whole with its check holding were one file whose passes a misread split apart, and are one again. A file sent in numbered parts — NAME.000, NAME.001 and on, of one time — is also joined into one, NAME, once every part is whole. Most of a service's files are in one of three containers of its own: a **file container** (opening `WTF1`: the address the file was fetched from, then a zlib stream, checked by its own Adler-32), an **archive container** (opening `WTZY`: the path the file was cached under, a record giving the file's name, the CRC-32 of the file and its times, then a stream imploded by PKWARE's Data Compression Library) and a **short archive container** (opening `WTZX`: the same with a shorter record, the name at its byte 8 and no times, and a path within the client's cache folder). An archive's path's length is one or two decimal digits ended by a zero, in a field of three bytes whose last a single digit leaves as it was; an archive's path opens with the cache folder (`cache\`), whose name is put right where one of its bytes was received wrong, and up to two other bytes of the path lost or received as no character a path holds are read as `_`, the mirror placing the file by what the rest of its path says; a response's `CachedURL` names its file whatever its path read. The stage unpacks all three, and the file a container holds stands for it, named by the last part of its address or by its name, with the address or path kept; a container broken off where its bytes went missing gives its file as far as it unpacked. A container may hold the web server's whole response the client cached — its status line, its headers and an empty line, then the body: the body is the file, named and placed by the address the response's `CachedURL` header gives, and the response's head is kept with the file as received. Each frame's header bytes 2-3, a check of the service's own, fit no CRC or sum of the frame and are not used. The frames themselves, the pad taken off and in the order of their counts, are written beside the stream as `mydata.t33.datacast-0F0-0FF.<service>.frames`, 416 bytes a frame, the frames read whole.

In the viewer a datacast is an item of its own, showing how it decoded and the text it holds, and each file follows: a GIF picture drawn as the raster it is, a page of HTML as the text it shows, a text file as it reads and anything else as a dump of its bytes, then the text it holds — every run of twenty printable characters or more that reads as words (a space among it, letters at least half of it), a line each, as a document's text or a program's messages are held. A framed service is an item too, with its frames' counts, objects and containers and the headers of its first frames. A file is marked incomplete where bytes of it no copy delivered or its container broke off, and its description says whether its service's check of it holds. The report's **Files** line under **Datacasts decoded** counts the files by kind and framing, with the checks that held and the bytes no copy delivered, and a **Framed** line a service says how its frames and objects read.

**Website mirror.** The framed services' client — a Windows program that showed the services' pages in an Internet Explorer window — kept every file it received in its cache folder by host and path (`cache\<host>\<path>`) and served the pages from there as though from the web. With `export_records` the stage lays the files the framed services sent out the same way, beside the stream in `mydata.t33.mirror/`: each at `<host>/<path>` from the address its container gave — a URL with its scheme dropped (a misread one too), or a cache path with its cache folder dropped — `\` read as `/`, a folder's address as its `index.html`, the host in lower case, `..` stopping at the host, and any character a file system would not take as `_`. A file sent with no address goes under `_files/<addresses>/`. A file not received sound — not whole, its check failing, or its address read in part — in a folder no sound file is in or under is taken to have had its address misread: it goes to the sound file of its own name whose address as sent is as long as its own and differs from it least, in at most one byte in eight (three at least); or else to the one folder a sound file vouches for that is as long as its own and differs from it in at most two bytes, looked for from its own folder up to its host — case ignored, and a tie placing nothing. The manifest keeps the address as sent. An address sent more than once keeps every version whose bytes differ, in the order received: the last version received whole is written at the address, and with more than one each is written beside it as `NAME~1.EXT`, `NAME~2.EXT` and on. A damaged copy — cut short, or with bytes missing — that agrees with a version over at least the first quarter of its bytes is a copy of that version, and a whole copy takes the place of a damaged one it agrees with. A page or style sheet is written with its links pointed into the mirror: each address in an `href`, `src`, `background`, `lowsrc`, `action` or `codebase` attribute, a style's `url()`, a refresh's `URL=`, and a full URL in a quoted string — a script's, a list option's value — is read as a browser would read it from the page's place, and found in the mirror without regard to case, as the client's file system found it, a folder's address finding its `index.html`, `index.htm`, `default.htm` or `default.html`. A link the mirror holds is pointed at it relative to the page, its query and fragment kept (a page can read its query); one it does not hold is made a full URL to where it pointed on the web; and a folder's URL a script joins more onto points at the folder. Script, mail and in-page links, the page's text and the original address a site-copying tool kept in a `tppabs` attribute are left alone. Such a page, and a file cached as a web server's response, is also written as received under `_received/`, the response with its head. The mirror's `index.html` lists each host's start page and every address with its versions, and `manifest.tsv` has a line for each version: its address, version number and count, whether it is the one at the address, where it was written, its time, bytes and kind, whether it arrived whole, its check, its address as sent, the addresses that carried it and its copies. The report's **Mirror** line counts the addresses, hosts, addresses sent again changed and files placed back from a misread. The pages were made for the browser of their day: some draw with its own object model (`document.all`), embed its ActiveX controls (its data-binding control fills a table from a text file sent beside the page), or ask the client's own control — an object on the page — for files from its cache, their times and the viewer's settings, and draw what it returns; a browser of today shows those parts only in part, or not at all.

**Encoder idle fill.** The idle fill of the Ross Video (Norpak) encoders comes as data groups of type zero — a group header, a record header, then 65 blocks of the test pattern — which the record layer would read a record out of like any other, catalogued as a page F00/000 that no service ever sent. A data group whose bytes are the pattern — of at least 64 pairs of unequal neighbouring bytes that arrived, half or more each the one before it shifted a place, where the fill gives nearly all of them and teletext about one pair in sixty-four — is kept from the record layer, and so is a group too short to judge on an address that has already carried one; the report's **Idle fill** line counts them. The packet stream keeps them, as it keeps everything.

**Presentation (§6.1).** A record of type 0, 1 or 3 carries NAPLPS, which is interpreted into a display list of primitives — text, lines, arcs, rectangles, polygons, mosaics and redefinable characters, with their colours and their positions in the unit screen. A record of type 2 is an application record instead, and its data is decoded as the function descriptors of §7.2.2 rather than drawn.

Each record is presented the way a receiver would present the page. A record whose support-needed flag is set (§5.2.7.9) is drawn after its data channel's support record — address FFF with the support-record flag — so the macros, redefinable characters and colour maps a service defines once and shares across its pages (§8.7.1.4) reach the pages that invoke them. A record carrying the caption flag is drawn from the caption preset of §5.2.7.3: white text over black in colour mode 2, starting at the lower left.

A record may name a More Record — explicitly, in a header extension field (§5.2.8.4), or algorithmically, by its more flag and its long address plus one (§5.2.7.6, the last two digits counted in decimal per §7.3.4) — and that continuation is presented over the display its predecessor left (§5.2.7.8): a chain repaints only what changes between its screens. §7.3.4 has a receiver consult the header extension first and reach the more flag only where there is none, so a record whose header redefines its More Record never continues into its long address plus one. The extension names a record in the same data channel (record address 0, a short address or a long one), a record in a data channel it names as well (a channel and a short or long address), or a macro. Only a record in the page's own data channel is followed here; one in another channel, or a macro, is shown in the record's details and followed no further, though it still keeps the more flag's address out of the chain. Both decoders of the day were put to the test with streams built for it, and both follow the extension over the more flag in every form — ES 3, ES 6 in the page's channel or another, with the flag set or clear. That holds even where it looks like a slip: a story whose last pages name the Master Index as their More Record went back to the index one page early on both decoders, and the story's last page was never shown. The viewer lists that last page and draws it on its own, which is how it looks without the pages it was written to follow. A macro outside 2/0 to 7/15, or a field of a size §5.2.8.4 gives no meaning, is read as though the field were not there, as §5.2.8.4 says a receiver is to. Where a recording holds several versions of a chain member, or of the support record, the highest is the one used, except that a version no copy ever named as transmitted does not displace one that was (see **Addresses the recording named but the service never sent**): a page filed under a misread identity would otherwise stand in for the page a story continues. And where an identity carries more than one content (see **Records**) and the latest at an address continues into nothing, the chain is followed through a content of the same identity that does continue it: a page rewritten as text may still be sent beside an older content of the same identity whose More Records carry the frame and colours the pages after it draw over, and taking the rewritten content for the chain would leave those pages drawn without them. The older content is still listed under that identity, and drawn over the page it was sent beside, as a receiver given that copy drew it. Only a link forward continues a page. A link back to the same or an earlier address — an index page naming itself, a story naming the Master Index (000) as its More Record, the last page of a rotating set naming the first — returns the reader to a page that stands on its own and is reached by its number as well as by MORE, so that page is presented as itself rather than over the one that named it, and a rotating set comes out as one chain from its lowest address. Each member of a chain is therefore drawn over the accumulated display of the members before it, and the viewer lists the chain as one page, marked with a sub-page count in the records list, whose members are stepped through as sub-pages the way the teletext viewer steps a multi-page set.

A page can be written to be drawn over the page the viewer asked for it from. The Panasonic TU-2000x does not clear its screen when a new page is asked for — run as firmware on a recorded stream, it keeps whatever is on screen until the new page clears it — and a service can use that. A quiz played by page number is one way: a board page clears the screen and draws numbered squares; each square's page starts without clearing, marks its square and writes its question beneath, with answers by page number; and each answer draws over the question — a wrong one putting the square back, a right one drawing a piece of a picture in it, so that a viewer who answered every question had assembled the whole. Rotating highlight cards drawn over a highlights page, each redrawing only the middle of the screen, are another. So a page that neither clears the display (CS, or RESET's display action) nor fills the whole display area before it draws anything else is presented over the pages a viewer came to it through, found the way a viewer of the TU-2000x moved. A step from one page to the next is surest where the first page's header names the next for MORE, NEXT or INDEX (§5.2.8.2), less sure where its text offers the next page's number, and least sure where the next page is the one after it by number, which its NEXT reached. The way taken starts at a page that stands on its own, passes only through pages that draw over the page before them, holds at most four pages, and is the surest such way, then the shortest: an answer of a quiz is drawn over its question and the board, and not over a copy of the question the board's NEXT brought up. Each page of the way is drawn as the viewer saw it, a More Record over the members of its chain before it, and the page's own More chain is drawn over the way with it, up to a member that clears. The line under the page says what it was drawn over. Every other page is presented as before: those that clear or fill the screen are unchanged by what came before them, and pages that carry two classification pointer bytes, which neither surviving receiver accepts, are drawn on their own, since how a receiver changed page under them is not known. So is a page no copy of which arrived whole with its suffix check passed — every page of a service that sends no check — or whose first bytes no copy delivered: a damaged page may have lost its clear rather than been sent without one, and drawn over another page its damage would read as that page's. The Norpak TTX 650 does clear its screen on a page request, so it showed such pages on black.

The pass also learns about the recording as it goes, and spends less on later frames than on the first ones: where in the line this recording's data bursts start, and which of the candidate lines carry them at all. Once enough lines have yielded packets, the search for where each line's data burst starts narrows to where this recording's lines have already been seen to start; a narrowed search that finds nothing is repeated over the full window, so this costs a few percent on empty lines and cannot lose a packet. After the first frames, only the candidate lines this recording has been seen to carry data on are read, and the full window is rechecked periodically, so a service that starts part way into a recording is still picked up.

Recovering a line reads that line's samples and nothing else, so frames are decoded on several threads at once while the packets are written from one, in the order they were transmitted (`decode_threads`). The recovered stream does not depend on how many threads were used.

## Tools

### NABTS Records

The record viewer for this node. Triggering the node opens it automatically, which is how the records are reached — leave `output_path` empty and triggering is a decode-and-browse that writes no file.

The catalogue stays with the stage after the run, so closing the viewer and picking **NABTS Records** from the **Stage Tools** menu re-opens it immediately, reading what the last trigger produced rather than decoding the source again. That menu entry only ever reads: on a node that has not been triggered it says there is nothing to show instead of starting the decode, because deciding when to spend that time is what **Trigger Stage** is for. Editing any stage's parameters rebuilds the graph and discards every stage's results, closing the open viewers with them — trigger again for a catalogue that matches the new settings.

The viewer lists every record the range carried: its channel and record address, its version, the record type, how often it was seen and over which frames, the section of the service it belongs to, and the classification flags the service set on it. Because the catalogue comes from a pass over the whole source rather than a window around the preview position, the list is the service's full carousel rather than whatever happened to be on screen.

**Page** finds a page by its number, the way a viewer of the day asked for one. The Panasonic TU-2000x took the digits typed before ENTER and set them right-aligned at A7 of the nine-digit long address (§5.2.5): three digits are a short address — 150 is 0000 150 00 — and four reach the long addresses a service gave its larger pages, so 1985 is 000198500; a More Record, whose last two digits are its own, is reached by its whole nine-digit address, and pages with a hexadecimal digit in their address (the support record FFF, the Cyclic Marker F00) have no number. An address the recording carried in several versions comes up as its page, its versions stepped as sub-pages; a More Record by its own number comes up as the sub-page it is of its chain.

The **Section** column says which section of the service a page belongs to, where the service said: the page its header names as its Index Record (§5.2.8.2 meaning 011) — the news pages naming the news index, the weather pages the weather index — or, where the service flagged its section indexes instead (§5.2.7.2 Y13), the flagged page at or below the page in the same hundred. A page the others name as their index is in its own section. Where a page's header names no index, the section is the one the Master Index's list of sections puts it in: a Master Index can list where each section starts ("1.News 10.Weather 20.Finance ..."), and a page is in the section whose start — an entry of that list, or an index the pages name or flag — is the nearest at or below its number, provided the pages from that start to it run on with no more than five numbers unused between two of them. An entry no page names as its index takes the index the pages of its range do name, where they agree, and is its own otherwise. So a section's bumpers ("Stay tuned for the latest: Finance") and the advertisements among its pages go with the section they stand in, and a page beyond the last entry or past a run of unused numbers — a quiz numbered apart from the rest, a special cycle — is in none. Tried on pages whose header does name an index, as if it named none, the list gives the same section for nearly all of them; the rest are pages under a sub-index the list does not give and a few whose header names the section beside their own. The Master Index starts no section, even where section indexes name it as theirs. Only the column groups pages so: INDEX still goes where the decoder took it. A service that names no sections has none.

**Back**, **Index**, **Next** and **More** beside the page box move between pages as the decoder's keys did, and the numbers the page on screen offers are listed beside them as links. NEXT goes where the page's header names its Next Record (§5.2.8.2 meaning 010), else to the next page by number (decimal, so 009 steps to 010); MORE to its More Record (§7.3.4); INDEX to the record the header names as its index, else to the section's index page, else to the Master Index, 000; Back to the page shown before. A key the page gives no page the recording carried is disabled, and its tooltip says where each one goes. The numbers a page offers are read off its text: page numbers after "p", "pg", "page" or "Press", an index entry's number at the end of a dot leader or of a row of capitals, every number of a row of nothing but numbers (a game board), and the numbers a list's rows start with ("151 silk", a quiz's "351 10 votes"), where at least two rows do and the first is not 1 (a ranking), or that an index set in columns puts before a colon ("24: Abbot-Anheuser   32: Kraft"), where at least two entries do and none is 1 (a legend of option keys); a table's dot leaders, which lead to scores and prices, and its rows, which go on to more figures after their titles, are not read as pages. A keypad can type into the page box a digit at a time, a new number starting once one has brought up a page.

**Games** are marked in the list, so they can be found: **Game: keypad** on a page played on the Option keys (see **Option keys** below) and **Game: quiz** on the pages of a quiz played by page number. What makes a page part of such a quiz is how the pages are put together, not what they say: a page drawn over the page that offers its number (see above: a decoder that did not clear its screen for a new page) is an answer to that page, where the page offers two or more such answers; and a page that offers two or more answers sets a question. A quiz's board offers the numbers of its questions, each drawn over the board, and each question offers its answers drawn over it — wrong ones and a right one — and a copy of a question the board's NEXT leads to, offering the same answers, is a question too: every page of it is marked. An index that leads to a single page drawn over it, as rotating highlights do, sets no question. Type **game** into the page box — or **Game: quiz** for one kind — and the list shows only the pages carrying the mark, the first of them on screen; **Enter** shows the next, **Shift+Enter** the one before, and the arrows beside the box step through them too. Typing a number, or following a key or a number to a page that is not a game, lists every page again. Any other mark in the list is found the same way: **~** for the pages drawn from rebuilt bytes, **unconfirmed** for the records kept without an attested address. Not marked are the quizzes a viewer only reads, whose answer comes by itself — on a countdown, with the next version of the page, or behind MORE: the viewer presses nothing the service answers, and only their words, not how they are built, set them apart from any other page.

An address that carried more than one record outside a More chain — a carousel giving each page in turn the next version (§5.2.7.2), a magazine edition replaced while the recording ran, a page revised — is listed as one page, marked with its version and page counts, whose records are stepped through as sub-pages in the order they first arrived. That is what a receiver asked for the address put on screen: §5.2.7.2's Update Flag has a page replaced as each new version arrives, and both decoders of the day, left on such a page in their emulators, drew its items one after another in that order and went on to a second edition when it replaced the first. A carousel with fewer pages than versions comes round with the same page under the next version, and such a page is one sub-page, labelled with every version it was sent under (`v0, v2`) and drawn from the record with the most copies that arrived intact. Two records are one page only where they agree on every byte both received unharmed — delivered, and passing its parity — as they stand or slid by up to the few bytes a misread header moves a record, over at least half of the longer record; and where the shorter one arrived intact, so that its length is its page's, a record more than those few bytes longer carries something it does not. So a page revised as it was re-sent stays a sub-page of its own however little changed — a quiz's next version drawing its answer, a standings table moving on by a game, a story's "today" becoming "Mon." — and so do the pages of one carousel that share a template, and a record that lost too much to be judged. A looser measure, seven bytes in ten agreeing window by window, would take two pages of one template, or two stories under one banner, for one page.

Selecting a record shows what it carries:

* A **presentation record** is drawn as its NAPLPS display list, beside the plain text of the page. Pages are drawn in a unit square whose lower 0.78125 is the display area every receiver is guaranteed to show (ANSI X3.110 Table D1); **Show display area** outlines it, which is how to tell a record drawn deliberately into one corner from one that was mis-scaled. The text pane is there because an index page is mostly words and picking them off a rasterised page is tedious — it is the same characters the drawing used, in reading order. A page that writes over itself has no reading order on the screen: a message longer than the display wraps back to the top (SCROLL OFF, the standard's default) until the lines stand on top of one another. For such a page the text pane lists the characters in the order they were sent instead, a line wherever the cursor started one, which is how the message reads. Words a filled rectangle or polygon drawn later covers for the most part are read a screen at a time, as a block of their own before the words that replaced them, blocks in the order the figures were drawn, then what the display holds once the record is done (a figure over a letter or two of a word, a picture beside it, leaves the word where it stands): a timed page may write one message after another into the same box, blanking the box each time, an index may take its opening headlines away under its menu, and a More Record writes its page over its predecessor's — and read where they stood the words would come out interleaved letter by letter with the words that replaced them. A word drawn twice a pixel apart, as a title's shadow, is read once.
* An **application record** is shown as its function descriptors, each with its code in the code-table notation §7.2.2 uses and its arguments.
* A **record sent with nothing to draw** — every byte of it a NUL, which X3.110 §6.1.4 makes a transparent control with no presentation effect, or bytes that arrived whole and draw nothing, no figure, character or clear, with nothing cut short, skipped or refused — is named for the role its header gives it instead of being drawn as a blank page, and stays in the list. A **Cyclic Marker** heads its data channel's cycle (§5.2.7.7; it is sent at F00), a **Support Record** at FFF shares nothing with the channel's pages (§5.2.7.12), and an **Auto Acquire → 020** record hands a receiver straight on to its More Record, which is the page a viewer actually saw (§5.2.7.8). One with no such role is marked **Empty record**. A record whose NULs stand in for bytes no copy delivered is not one of these: its page was lost rather than sent empty, and it is drawn as recovered. A record whose code only resets the decoder draws nothing either, and is marked **Reset only** and listed with its bytes: NSR puts the code sets, the domain, the text and texture attributes and the colour mode back to their defaults, and the cursor where the two bytes after it say (X3.110 §6.1.6.5), SO and SI choose the set the codes after them are read from, a RESET with no operand bytes or none asking for anything resets nothing (§5.3.2.9.3), and NUL has no effect. A service can send such a record on a timer whatever page its cycle is on, at an address no keypad could ask for; it carries no time or other data.
* A **record that is not NAPLPS** — another service's data sent under a presentation record type, such as a news wire, a test page or a block of binary data — is listed as that data rather than drawn, marked **Not NAPLPS** with a note of why. Read as NAPLPS such a record draws stray characters and shapes, overprinted where the text runs past the foot of the screen. A record is taken for data where at least 64 of its bytes arrived unharmed and they are binary data — transmission and device controls (SOH to ACK, DLE, DC1 to DC4, NAK, SYN and ETB, which X3.110 §6.1.4-6.1.5 gives no effect on a page) make up 8 % of them, three quarters of what random bytes hold, where a page carries a few at most — or plain text — lines broken by line feeds, with fewer than one byte in a thousand of the codes a NAPLPS page is built from (SO, SI, SS2, SS3, ESC, CS, CAN, APS, APH and NSR) and no More Record before it, since a chain's continuation may only add text — or text framed for a data link: 16 CR LF line ends or more with link controls among them, 2 % of it. Text is shown as text, a line end as a new line and any other control as `<XX>`; binary data in hexadecimal, sixteen bytes a line with their parity stripped. A Dow Jones test frame is named by its own header before any of that and listed as the text it carries: no SOH, STX, ETX or EOT of ANPA 1312 framing is in it, and what reads as link controls among its text are check bytes. Each copy opens with five fixed bytes and the frame's length, then blocks of 27 bytes, the first starting with the framing number five times and the block count in five decimal digits, every digit a Hamming 8/4 byte (CEA-516 §8.2). Framing 1 carries the text unchecked; 2 adds the fourteen-bit sum of each block's 25 characters (high seven bits, then low seven); 3 an exclusive-OR block after every three; 4 two blocks after every five holding each column's sum; 5 to 7 both a sum in every block and column sums after every 5, 8 or 13 blocks; and 8 a sum after every run of 5, 5, 5 and 4 characters with column sums after every five blocks. A check byte of 1 is sent as 7/15 rather than SOH. The codes the denser framings fill the text with are the framing, not damage. The listing gives the framing, how many checks held, and the text with the checks taken out.
* A record whose classification sequence carries **more than one pointer byte** (§5.2.7.1) is outside the Full Service Standard, whose receivers ignore such a record entirely (§8.5.2.7.1), and the period's receivers — the TTX 650 and TU-2000x — refuse it. It is read and drawn all the same, where the rest of its header and page is well formed, and the line under the page says **outside the Full Service Standard**. The same line lists any flag bytes §5.2.7.2 reserves that the service set anyway; what they meant was the service's own. The pointer count and the reserved bytes are voted from a record's appearances like its flags (see **Addresses the recording named but the service never sent**).

#### Choosing a receiver

**Receiver** at the top of the window chooses the receiver resolution the page is drawn against. There is no parameter for it, and deliberately so: nothing in the recovery depends on the choice — the records are read off the recording, and the receiver decides only how they are drawn afterwards — so picking one redraws the page you are looking at and leaves you on it, without reading the recording again. Making it a parameter as well would mean paying a full re-run of the recovery pass, which is what editing any parameter costs, to change something that pass cannot see. The window opens on **256 x 200**, the receiver the standard itself requires.

That includes downloadable characters: §6.2.3 sizes a DRCS character's storage buffer from the physical resolution its character field covers, and the presentation code is run when the page is browsed rather than when the recording is read, so those buffers follow the choice too.

ANSI X3.110 draws into an abstract unit screen, but it sizes several things in the physical pixels of the receiver displaying them: §5.3.2.2.6 defines the logical pel — what gives a line its width — as covering "all of those pixels that lie under any portion of the logical pel as it is mapped to the display screen", and guarantees it "will always map to at least one and possibly many display pixels". Line texture dot and dash lengths (§5.3.2.4.2), hatch spacing (§5.3.2.4.4) and the raster step of INCREMENTAL POINT are all multiples of that pel. A page therefore has no single correct appearance until a receiver is named; in particular a stroke the service left dimensionless is one *pixel* wide, and without a resolution there is no pixel to measure it in.

* **256 x 200 (reference receiver)** (default) is the grid Table D1 item 10 requires of a receiver — "resolution shall be on the order of 256 pixels horizontal by 200 pixels vertical" — and so what a set-top decoder of the period put on screen. Choose it to see the page as its author would have.
* **512 x 400** and **768 x 600** are that grid at twice and three times, for a sharper reading of the same page. Appendix D Scope note (2) contemplates exactly this: a receiver exceeding the reference model "may produce more pleasing images". Each keeps the grid pixel square in unit space, so nothing the service drew is distorted.
* **256 x 200 (vector)** draws the reference receiver's page as resolution-independent shapes rather than pixels. Curves stay smooth at any zoom, which suits reading fine detail, but the staircase a receiver drew a slanted edge with is gone. Everything else is measured in that receiver's pixels, as on the pixel modes: a stroke of a dimensionless pel is one of its pixels wide, and every point a record plots — a line's ends, a rectangle's corners, a polygon's vertices — lies on the pixel the receiver put it in, so a line, a frame or a filled figure covers the pixels the receiver lit and no others. The dots and dashes of a dotted or dashed straight line fall on the receiver's pixels too, their pattern taken from the screen rather than from the line's start, as the pixel modes draw it (below). Driven through the firmware of both receivers of the day with lines, rectangles and pels of every sign laid on their grid, it draws what they draw pixel for pixel. A figure that a page draws and then, at the same moment, draws again in the same place in another colour — a sparkle, or a shape put right — is listed once, in its later colour: a receiver showed only that, and the earlier shape drawn beneath it with smooth edges would show as a faint fringe round it.

The choices are named after the grid rather than by the 240p/480p shorthand a television is described by, because that shorthand counts the lines a set *scanned* and these count the pixels a decoder *drew into* — the reference model's buffer is 200 rows whatever the set showing it scanned, so calling it 240p would invite reading 240 rows into it.

Only whole multiples of the reference grid are offered. A page is authored against that grid, so at twice or three times everything its author placed on a pixel boundary lands on one again; at some fraction in between it lands between pixels, which thickens strokes unevenly and — because a character pattern is a bitmap of a fixed cell — breaks the letterforms outright.

The three pixel modes deposit the page into the receiver's frame buffer exactly as the standard describes and show you those pixels. The pixels are drawn as scalable blocks, not as a fixed-size image, so they stay sharp at any window size and in an exported PNG.

Everything the standard sizes in logical pels — stroke width, the dot and dash lengths of §5.3.2.4.2, hatch width and spacing, a programmable fill mask's step and repeat — comes out at that size in every mode, so a figure keeps its weight and its texture whichever receiver is chosen and however large the window is. A pel narrower than a pixel is widened to one from the drawing point's corner, in its own direction, so a dimensionless pel covers the pixel the point is in: "the physical picture elements (pixels) through which the infinitely small locus point passes" (§5.3.2.2.6), the pixel Appendix B's truncation maps a point to, and the one both receivers light — never a pixel's width straddling the point. A pel of negative width or height is laid from the pixel the drawing point falls in, back along that axis, as both receivers of the day lay it; §5.3.2.2.6 puts the drawing point on the pel's corner, which for a negative size leaves that pixel out. Stripes drawn with a pel one pixel wide and minus one high sit on the rows the receivers put them on. A stroke is as heavy as the pel is across the axis it runs nearer, whatever its slope — a one-pixel pel draws one pixel a column on a shallow diagonal — because a receiver's "straight line algorithm" (§5.3.2.2.6) puts the pel down once a step along that axis; dragged corner to corner, the pel would make a diagonal half as heavy again. The vector mode sweeps it the same way and puts the pel down whole at a line's ends and a figure's corners. The pixel modes step a texture along a line one grid cell at a time. A dotted or dashed straight line takes its pattern from the screen, as the receivers of the day laid it (see the pixel modes' dots below), and the vector mode draws each run of pixels that pattern lights as one stretch of the line, so its dots and dashes fall where the pixel modes' do and the dot leaders of a page line up in both; along an arc, which turns as it goes, the vector mode counts the texture in pels along the curve from its start.

The built-in character patterns follow the receiver like everything else. §5.1 leaves them to it — "the particular patterns (font) chosen for the characters are implementation-dependent and are constrained only by the specified character field at each size for a given display resolution" — and a set with more pixels had a character generator with finer patterns, not the same coarse ones magnified. **256 x 200** draws from a 6 by 10 face, which is both the cell Appendix B arrives at from first principles ("the most readable characters in this size range are 6 pixels by 10 pixels") and exactly the character field that grid gives the standard's default text size; **512 x 400** draws from a 10 by 20 and **768 x 600** from a 9 by 15 at double size, so text sharpens with the rest of the page rather than staying blocky in the middle of it. All three are members of the public-domain X11 "misc-fixed" family, so the letterforms are of a piece across receivers, and the face is chosen per character field rather than per page: a field too small for the finer patterns takes the 6 by 10, which is what a receiver with one generator and a field below it does.

A heading is drawn in a larger face than the text around it, as the receivers of the day drew it. The Norpak TTX 650 and the Panasonic TU-2000x each carried two character generators — a normal face on a 6 by 10 cell and a larger one on an 8 by 12, with capitals nine rows tall rather than seven — and drew either at whole multiples of its cell, each axis taking as many as it holds. Driven through both firmwares with every field from 4 by 6 to 32 by 40, the TTX 650 draws a field in whichever face leaves fewer of its columns and rows over, and the larger where the two leave the same (the TU-2000x weighs the rows alone, which comes to the same choice on nearly every field pages use). A title set in an 8 by 12 field — the TU-2000x's larger cell — or an 8 by 13 comes out in the larger face, a 12 by 20 field in the normal face doubled, and a 16 by 24 in the larger face doubled. The larger face is the misc-fixed 6x13, whose capitals are the TTX 650's own pixel for pixel, without its top row (which only five accents reach) and centred in the receivers' eight columns. The choice is made at the 256 x 200 grid, where the receivers drew, so a heading stays larger than its text at every resolution; the larger face has no finer member in the family, so **512 x 400** and **768 x 600** draw it at twice and three times its size. Downloadable characters have always followed the receiver, because the service sizes those itself (§6.2.3).

A character field covers the pixels its edges fall in — from the pixel its left edge is in up to, but not including, the one its right edge is in, and likewise up — which is how Appendix B maps a position onto the physical pixels. The standard's default field is 6.4 pixels wide on the reference receiver, so its fields are six pixels wide in some places and seven in others, but a line of them tiles its row with nothing left between two fields and nothing drawn by both: a background, a reverse-video field or an underline runs unbroken along the line. The letter is always the face's pattern at a whole multiple of its size, never stretched to the field, centred across the field with an odd spare column left as space to its right, and raised where the field is taller than it so that the baseline sits a fifth of the way up (Table D1 item 2). A downloadable character is laid the same way from its own buffer, whatever width the buffer was defined at.

Rotation turns the character field counterclockwise about its origin (§5.3.2.3.2, Figure 17): at 90 degrees the field lies above and to the left of its origin with the letter's top pointing left, at 180 below and to the left, at 270 below and to the right. A negative field width or height mirrors the letter inside its field and leaves the field where it is, since "the character field origin is the lower left corner of the character field ... regardless of the sign of the character field dimensions"; mosaics are mirrored and turned like any other character. Underline mode (§6.2.7.15) draws a line along the foot of every field, as thick as the logical pel is tall, and turns mosaics separated instead: each lit element loses the pel's width from its right and its height from its top, and never less than one pixel, so separated mosaics always look different from contiguous ones (Table D1 item 6). A mosaic's six elements divide the field's own pixels at its halves and thirds, so neighbouring mosaics meet exactly, and in reverse video the field is drawn around the lit elements as it is around a letter.

The supplementary set is drawn from the same faces as the primary set: fractions, arrows, quotation marks, the musical note, the Latin letters of columns 6 and 7 and the rest. An accent (column 4, Tables 26 and 27) is sent before the letter it goes over and leaves the cursor where it was, so the letter lands in the same field; the two are drawn as one character — Table 18's accented letters from the face's own pattern, any other pairing with the accent laid over the letter. An accent no letter follows, or one followed by SPACE, is shown on its own in its spacing form. A letter that comes after a WAIT keeps the accent the earlier stage already showed, and one whose field was drawn over in the meantime is drawn on its own. Table 25's full lines, diagonals, cross and filled half-field triangles are drawn from the field's edges and corners, so a run of them joins into one line or one edge. A character the faces hold no pattern for is shown as a hollow box a capital high rather than left blank (§8.3.3(3)). In the vector mode an accented letter is one character of its text run, the accent written after the letter as Unicode orders it, so the rest of the run stays in step.

A stroke comes out the pel's weight wherever it falls on the grid and whichever way it runs: a one-pel line is one pixel across drawn horizontally, vertically or on any slope between. The standard sizes the pel without reference to either, so a line that grew a pixel where it happened to straddle a pixel boundary, or where it turned a corner, would be showing the grid rather than the page. A filled figure and the same figure outlined agree pixel for pixel, so a service that fills a shape and then draws its border — as a weather map does with each region — gets a border with no colour showing past it and no gap behind it.

**Save PNG…** writes the same size whichever is chosen — 1536 by 1152, a whole multiple of every grid across. Comparing one receiver with another is what the choice is for, and images of different sizes would make the comparison about the sizes instead.

Whichever is chosen, the page is displayed in a 4:3 area: §4.2.2 puts the guaranteed-visible unit screen — x 0 to 1 and y 0 to 0.78125 — in the display area of a television set, which makes the receiver's pixels slightly wider than they are tall.

**Enable animations** plays the record the way a receiver put it on screen, on the timing the record itself carries. The stage works that timing out when it reads the record; the viewer only plays it back, from the start whenever a record is selected.

* **Drawing in stages.** The WAIT command (ANSI X3.110 §5.3.2.8) pauses a receiver part way through a record, and services use it to present a page in stages — a credits page that writes one name, waits, and writes the next over the same line; a map that draws its coastline and then fills it in. Each stage appears once the pause before it has run out, and a clear part way through (CS, or RESET's screen clear) blanks what the stages before it drew. Drawing between two pauses is instant unless **Receiver pace** is on (below); the record's own transmission time is not modelled either way.
* **Receiver pace.** A receiver of the day drew a page as fast as it could and no faster, so a busy page was seen being built up and took seconds to finish, pauses or none. With **Receiver pace** ticked every command takes what the Norpak TTX 650 took over it, measured by running its firmware over blocks of crafted commands, in the pixels of its 256 x 200 screen: a character 3.4 ms in a cell the size of its own font's (SPACE 1.6 ms, and 6.5 ms where colour mode 2 draws a background) and 10 ms and 0.4 ms a row of the cell in a larger one; a line 3 ms and 0.29 ms for each pixel it plots, a horizontal run being nearly free; a filled rectangle 3.5 ms, 0.32 ms a row and 2.8 µs a pixel, as far as it is on the display; a polygon by its vertices, rows and pixels; an arc by its length, 1.4 ms a pixel, so a circle of radius 90 takes most of a second; a clear 169 ms in every colour mode; and the commands that draw nothing their own few milliseconds — SET COLOR 3.1, TEXT 10.8, a size control 9.5, each drawing command 3.5 before its figure. Against the TTX 650's own drawing of the recorded pages, that puts three stages in four within a quarter of their length. The time left over from a whole millisecond is carried on, a pause starts once what came before it is drawn, and a colour loaded part way through a stage shows from that moment, as it did on both receivers. What is drawn is the same either way; only when each figure appears moves. It is off to begin with, and like the other controls it redraws the page without reading the recording again.
* **TU-2000x pace.** The Panasonic TU-2000x, a home decoder of the day, drew a page at a pace of its own in its firmware: with **TU-2000x pace** ticked, on its own or with Receiver pace, every command takes what the TU-2000x took instead, measured from its firmware the same way. It drew a character in 4.7 ms — about as fast in a field twice the face's height, which it fills from the same ROM pattern (6.1 ms at 6 by 20), and by the field's area once the face is drawn at twice its width (20 to 28 ms at 12 by 20, up to 0.8 s for the largest), the face being the one whose cell leaves the fewest rows over; it plotted every pixel of a line, 0.18 ms on an axis and 0.65 sloping; it filled a polygon at two to three times the TTX 650's cost (10 ms a vertex, 1 ms a row) and drew an arc at a little over half of it (0.79 ms a pixel of its length); it cleared in 70 ms; and it loaded a colour in the vertical blank, so SET COLOR, BLINK and BLINK START wait for the next field, 8.4 ms on average over the pages' own mix. Against its own drawing of the recorded pages its table puts 86 % of stages and 88 % of pages within a quarter of their length, where the TTX 650's table puts 65 % and 58 % there; on the TTX 650 the two come out the other way round (77 % against 57 % of stages). On the pages both drew, the TU-2000x took a median 1.12 times as long as the TTX 650. A second box rather than a choice in the Receiver list, because the receiver a page is timed by is independent of the one it is drawn for; ticked with Receiver pace, the TU-2000x's pace is the one that plays.
* **Fills and clears sweep across the screen.** At a receiver's pace a filled rectangle, polygon or arc, and a clear, appear a row at a time over the time the receiver took, as the sets drew them: down the screen from the top on the TU-2000x — as a head-end decoder of the day drew them too, at about 0.75 ms a row — and up it from the bottom on the TTX 650. A clear sweeps the display to black, or to the colour it clears to, over the old picture, which shows in the colour map a RESET has just reloaded, as on the TTX 650. The viewer moves the sweep on once a field of the television, every 1001/60 ms, and a whole row of the receiver's grid at a time, and the saved SVG plays the same rows at the same moments. Lines, outlines and characters appear whole when they are drawn, a character being a few milliseconds; a still, and a page played without a receiver's pace, are as they were.
* **Blinking.** A blink process (§5.3.2.7.2) belongs to a **colour map entry**, not to a figure: it periodically overwrites the entry with the contents of a second entry, so what alternates is everything drawn in that colour, whenever it was drawn — and everything drawn in any other colour stands still, even if it was drawn after the BLINK command. The second colour is the one the record names. §5.3.2.7.3 lets the BLINK command point at any map entry, so a blink is not necessarily an appearance and a disappearance: a figure alternating with another colour twinkles, and one alternating with the ground vanishes and returns.
* **Blink timing.** Each process keeps the ON and OFF intervals the record gave it, in tenths of a second (§5.3.2.7.3), so two processes set up with different intervals blink out of step, as they did on a receiver. A start delay is measured, as §5.3.2.7.2 has it, from "the start of the ON interval of the most recently defined active blink process" — the one under way where that process is in an ON interval, its next where it is between them, or where the start so found has already gone by when the process is defined, the next after that, as both receivers of the day count it — which is how a service makes lights chase each other along a sign. A process defined with none running starts on the next tenth of a second of the page's clock, the tick both receivers step their blinking on. Processes whose intervals end together run newest first, each taking the colour map the one before it left — and so do processes defined together, at their first ON interval, as on the Norpak TTX 650. A process starts after whatever else the record did at the same instant, so a colour written straight after the blink is defined is the one it blinks against.
* **Colour depth.** Colours are kept at four bits a gun, 4096 of them. Table D1 item 5(4) asks a teletext receiver for 512, three bits a gun, as a floor; CEA-516 §8.6.3 has services choose from 4096 so that pages look right on both, the reference colour map of the standard's authors holds twelve-bit colours (US 4,439,759), and both receivers of the day have four-bit converters. At three bits, greys a page sends that differ only in their fourth bit merged into one band. A colour operand shorter than four bits a gun is scaled to the full range — its largest value is full intensity (§5.3.2.5.1), so white can be sent in a single byte — as the Norpak TTX 650 reads it; the Panasonic TU-2000x zero-fills it, and shows a one-byte white as a light grey.
* **Colour changes.** A map write is shown the moment it happens and reaches every pixel drawn in that entry, before or after (§5.3.2.5). That includes pixels drawn in colour mode 0: mode 0 finds or claims an entry for its colour, and a receiver stores that entry. A page that loads its palette after a pause therefore changes colour then. An entry mode 0 found its colour in counts as used from then on, as one it claimed does (§5.3.2.5.1), so a colour the page brings in later never takes it over: a page that draws its ground in a grey the default map already holds and brings in new colours after keeps the grey, as both receivers of the day do.

Clear the box to hold the finished record still — every stage drawn and every colour at rest — for reading or capture; ticking it again plays the record from the start.

A record that changes as it is shown has playback controls under the drawing while animations are enabled, the way a player for a moving sign works:

* **Play** and **pause**, and **Replay** from the start. A record that settles plays until two seconds past its last change, so the finished page is seen before anything starts again, and then stops there; played again, it starts from the beginning. A record that blinks never settles: it plays until its blinks have gone once round a cycle they all share — from the moment its last stage is up, for a period every blink's own period divides — and then goes round that cycle again for as long as it is shown, the page held with its blinks running, as a receiver held it. Where the blinks share no cycle as short as ten minutes, the longest of their own periods is used, and the ones that do not divide it jump at each turn.
* **<** and **>** hold the display before and the next one: the start of the display on screen, a stage or a blink turning, and pause there. The slider seeks anywhere in the record, playing on from there if it was playing; the clock beside it shows where the record is and how long it is, in minutes, seconds and hundredths.
* **Speed** plays the record at a quarter, half, twice or four times the timing it carries; **Loop** starts it again from the beginning each time it ends, instead of stopping or holding. Both stay as they are from one record to the next.
* With the drawing clicked, **Space** plays and pauses, **Left** and **Right** step, and with **Shift** they seek five seconds.

What is on screen at any moment is what the SVG **Save SVG…** writes shows at that moment of its own animation: both are drawn from the one timeline. The SVG plays the record once, at the speed it was timed, with its blinks running on.

What the standard leaves to the receiver is decided as follows, and the unit tests pin each reading:

* A WAIT opens with the format byte of Figure 28 (5/12), and §5.3.2.8.2 makes one that opens with anything else a null operation — as both receivers of the day do, whether the service sent it that way or the tape changed the byte. The tapes usually change two of its bits, which parity cannot see, so such a pause is lost here as it was on a receiver; only a format byte that arrived failing its parity can be put right, by **Reconstruct lost data**, from another recording of the page. A zero interval is two television fields (33 ms), the shortest Table D1 item 5(6) allows a teletext receiver. The clock stops at fifteen minutes, so a damaged WAIT cannot push the rest of a page out of reach.
* A blink process copies the second entry's colour at the start of each ON interval, as "substitutes the current contents of another entry" says; a write to the second entry during an ON interval reaches the blinking figure at its next one. The record's own map writes at an instant land before the processes due at that instant run. Ending the last process on an entry puts back the entry's own colour — the one it last had written, so a SET COLOR made meanwhile is what comes back (§5.3.2.7.4).
* BLINK START (§6.2.8.1) leaves its intervals to the receiver: here the drawing blinks to nominal black for a second and shows for a second, as the TTX 650 decoder has it. In colour mode 0 it first copies the drawing colour into a fresh map entry, since §6.2.8.1 has objects already drawn in the colour "remain not blinking".
* A coordinate command sent with no data at all is read as §5.3.2.2.5 reads any short operand, with zero bits supplied: POINT SET (Absolute) and POINT (Absolute) go to the origin, the relative forms stay where they are, the visible forms draw a point there, and LINE (Absolute) draws a line from the drawing point to the origin. An encoder can open and close every PDI section with an empty POINT SET (Absolute) and draw on from the origin it leaves. The Norpak TTX 650 and the Panasonic TU-2000x both read these commands so. Every other coordinate command with no data stays a null operation, as the TU-2000x has it; the TTX 650 draws a pel for them, at the origin for the SET forms, which pages written for the TU-2000x can send by the thousand and would not survive.
* An INCREMENTAL POLYGON keeps its first 256 vertices, the limit the 1993 Addendum to T.101 Annex D (clause 8) gives it — "the same as for the POLYGON command" (Table D1 item 4) — as the Norpak TTX 650 does and as POLYGON does here.
* A drawing command the page record itself ends inside — no code after it to end it — is drawn as far as the words that arrived whole: a partial last word is not zero-filled, and a figure only its last word closes (a polygon, an arc, an incremental polygon) is not drawn. Both receivers of the day keep a command open until the code after it arrives, so neither ever drew these; a record ending mid-command has almost always lost its last packet, and the zero-filled word draws a stroke the sender never sent. A short word a code ends is still zero-filled, as §5.3.2.2.5 has it.
* **Curves, ties, dots and fills in the pixel modes** follow the receivers of the day, run as firmware, where the standard leaves the choice to them. At 256 x 200 every coordinate a record sends is the corner of a pixel, and both receivers draw through those corners rather than through whichever pixels the true figure crosses, which would put every curve half a pixel below and to the left of theirs. So:
  * An arc or circle through three points is traced a pixel at a time, as the Norpak TTX 650 traces it: from the start, to whichever neighbouring pixel keeps nearest the radius about the circle's centre, round to the end. A filled arc is each row from the leftmost to the rightmost pixel of the curve and its chord, and its highlight leaves the chord out (§5.3.3.3). Three points on a line are drawn as two lines, start to intermediate point to end. Pixel for pixel this is the TTX 650's drawing of every arc and circle tried, and on the recorded pages it makes most of the arcs both receivers drew alike — globes, eyes, birds' heads — come out as they drew them. A spline (an arc of more than three points) is still drawn as short straight segments within a fifth of a pixel of the curve.
  * Where a line passes exactly midway between two pixels, the upper one is lit, as both receivers light it on a line drawn upward, so a line draws the same pixels whichever end it starts from.
  * A dotted or dashed straight line takes its pattern from the screen rather than from its start: a pixel of the line is lit where its column (its row, on a line steeper than 45 degrees) falls on a lit part of the pattern, the TTX 650's dotted lit for one pixel in every two pels, dashed for two pels and a pixel in six, dot-dashed for one pixel and then two pels and a pixel in six. Both ends are drawn whatever the pattern says there. Dot leaders on different lines of a page therefore line up.
  * A filled figure is its traced outline and every pixel whose lower left corner lies inside it by the odd-even rule (§5.3.3.5.1), as the receivers fill one, a row at a time between the outline's crossings. A gap a single pixel wide inside a figure stays open, as on both receivers.
* DELETE (7/15 with the primary or supplementary set invoked) is a null operation (§4.4): nothing drawn, the cursor not moved.
* BEL (0/7) is the "transient indication" of §6.1.6.2, a bell or a flash, and is a null operation here: nothing is drawn or sounded. A BEL on a recorded page is nearly always damage: most fail their parity, and many of the rest are an ordinary drawing byte in another recording of the same page. The Norpak TTX 650 beeps for half a second at each one.
* Sixteen processes run at most (Table D1 item 5(5)); a seventeenth is refused.
* A cleared display is nominal black: map entry 0 in colour modes 1 and 2 (the X3.110 definition), and black with no map entry behind it in colour mode 0.
* A More Record (CEA-516 §5.2.7.8) opens on the display its predecessor left, already drawn, and a blink process nothing terminated goes on running into it in the same phase; the Support Record's processes likewise carry into the page.
* Once the page has finished drawing, the processes still running repeat for as long as it is shown. The viewer is given one cycle of them — as long as the least common multiple of the periods of the processes that copy colours between each other — and repeats it. Periods with no common multiple under ten minutes are cut to the fastest that fit; the log counts those at debug level as each catalogue is built.

How the page itself is drawn follows the standard in the same way, including where it leaves the choice to the receiver:

* **Off the screen.** §5.3.1 makes a drawing that leaves the unit screen an error, and lets a receiver handle it either way: "this PDI may either be rejected (ie, executed as a null operation) or executed and clipped within the unit screen". Points, lines and rectangles keep the geometry the record gave them and are clipped where they are drawn, so a rectangle running off the edge is cut off by it rather than squashed against it — as both receivers of the day clip them. A polygon, arc or spline with a vertex off the unit screen (x or y below 0, or 1 or more) is rejected instead: not drawn, though the drawing point moves as the command would have moved it. That is what the Panasonic TU-2000x does, driven through its firmware; the Norpak TTX 650 clips them. A service writing to the standard never sends such a figure (§8.2.1 (4)), and on a recording one nearly always comes from a lost stretch — the bytes after the hole are operands of commands whose opcodes were lost, and a figure that takes them in as vertices runs off the screen and, clipped, floods the page with a shape nobody drew — or from a damaged operand. A polygon of that kind can cover half a page; neither receiver draws it. The unit screen runs above the display area (§4.2.2), so a vertex up there is on it and the figure is drawn. The cursor alone is kept on the screen: text sent to a cursor off it would vanish, and §5.3.2.3.7 has the cursor follow the drawing point only as far as keeps its character field on the unit screen.
* **An operand that never came.** A command short of an operand has it zero-filled, as the 1993 Addendum to T.101 Annex D reads the standard ("for all PDIs, when not otherwise stated, non-existent operands are assumed to be zero"): SET & LINE (ABSOLUTE) with its start point alone draws a line from it to the origin, as both receivers of the day do, and the relative form a line of no length that leaves the drawing point on the start. LINE (Absolute) with no data at all is a line to the origin, which both receivers draw; LINE (Relative) and the SET forms with no data stay null operations, as the TU-2000x has them.
* **A byte known to be wrong.** Every data byte of a teletext record carries odd parity (CEA-516 §3.3), so a byte that arrived failing it — where the vote had no copy with a clean value for it — is known to be wrong, and it is not run as a control or a drawing command: a C0 control, ESC included, is dropped as the record is read, and a PDI opcode is skipped, its operands then data with no opcode in front of them. That is what the Panasonic TU-2000x does — its firmware flags the failure as it fetches each byte and skips a control or opcode carrying the flag — and the Norpak TTX 650 goes further, discarding the whole block such a byte came in. Run as what it reads as, a byte that was a shift or an operand clears the page or reads its drawing as text: a page can lose its whole picture to a CS failing parity where it sends SO. Driven through the TU-2000x's firmware with each page's bytes and their parity as received, the pages the rule changes come out closer to its picture several times as often as farther from it. A character or an operand byte failing parity is still drawn as its seven bits; the TU-2000x draws such a character as a checkerboard and abandons the command at such an operand. A record handed over without its parity — no byte with b8 set — has nothing to test, and is run as it is.
* **Text too small to read.** Table D1 item 2 asks for the primary characters to be presented only in fields of 6/256 by 8/256 or more. In a smaller one both receivers of the day present no pattern — the Norpak TTX 650 lights the one pixel at the field's origin, the Panasonic TU-2000x nothing — and this stage draws the TTX 650's dot, at every resolution and in the vector receiver, where it once squeezed the whole letter in. The same goes for a downloaded character in a field smaller than its buffer. On the recordings such fields come from damaged TEXT commands.
* **Proportional spacing.** TEXT's inter-character spacing code 3 is proportional spacing, whose algorithm §5.3.2.3.4 leaves to the receiver. Page creators could not then tell how long a line would come out, so the 1993 Addendum to T.101 Annex D (the same Data Syntax III, clause 11) fixed it: every character of the repertoire is in one of ten width classes, from the stems and points of class 0 to the full width of SPACE, M and W in class 9, and a displacement function turns the class and the character field's width into how far the cursor moves — in the default 6.4-pixel field an i moves 2 pixels, an a 5 and an M 6. Both receivers of the day lay proportional text out by it, and put each character's ink at the cursor rather than centring it in its field, which is what closes the gaps a fixed pitch leaves beside narrow letters; of twenty crafted lines, nineteen come out within 1 % of the Norpak TTX 650's. A composite character takes the wider class of its letter and its mark, APF and APB move the full-width class, as the Addendum has them, and mosaics and downloaded characters keep their field. Both receivers apply the function only where the path runs the way the character reads (right at 0 degrees, up at 90, left at 180, down at 270) and space a path against it by the field, and so does this stage.
* **Where text goes at an edge.** A character whose advance would leave the unit screen is followed by an automatic carriage return and line feed (§5.3.2.3.6) on whichever path the text runs. A line feed or reverse line feed past the display area wraps to its opposite edge, or with SCROLL ON scrolls the display area up or down by a line — the rows scrolled in black, or the background in colour mode 2 (§6.2.7.13-14). APF and APB past the end of a line go on to the next line or back to the previous one (§6.1.2.1-2). While the cursor's character field lies wholly inside the active field FIELD sets, all of this happens against the field instead (§5.3.2.3.6, §6.1.2.1-7, §6.2.7.3, §6.2.7.13-14 — "the active field used for columnated text"): a carriage return comes back to the field's edge, a line feed past its bottom goes to its top row, and REPEAT TO EOL and scrolling stop at it. A cursor whose field is not wholly inside runs free, and its carriage return goes to the display area's edge. A field of negative size is counted from its origin's own pixel, as both receivers count a logical pel of negative size, so pages that put the cursor's cell top on a downward field's origin row keep their text in the field. This is the Norpak TTX 650's reading, which is the clause's; the Panasonic TU-2000x also confines, but only needs the cell to overlap the field. A character field turned 90 or 270 degrees steps by its height along the path and by its width a row (§5.3.2.3.4-5). A turned field is laid from its origin's own pixel on each axis it runs back along — left of the origin at 90 and 180 degrees, below it at 180 and 270 — as both receivers lay it, driven through their firmware; counting from the pixel before the origin, as the field's edge alone would, put every rotated label a pixel off theirs. NSR without an address leaves the cursor where it was (§6.1.6.5(6)), and a TEXT whose field has no width or no height — what a field word cut short comes to — keeps the field there was, as both receivers do.
* **REPEAT** repeats only the character immediately before it, and from the set it came from (§6.2.7.2); anything in between — a carriage return, a colour change — leaves it nothing to repeat. REPEAT TO EOL fills the line to its last position on any path, and the line break after it is the automatic one.
* **Colour mode 2** draws the gaps of a dotted or dashed line, of a hatch and of a texture mask in the background colour (§5.3.2.4.2, §5.3.2.4.4), and a texture mask the record never defined fills with the background — in modes 0 and 1 it fills nothing (§5.3.2.4.4).
* **INCREMENTAL POINT** (§5.3.3.6.3) lays its colours a pel apiece from the drawing point, the packing counter's worth of bits each, row by row across the active field; a row that would leave the field ends there and the rest of its byte is dropped. A field that runs out of rows scrolls instead. The vector view scrolls a field that is the whole display area — as it scrolls SCROLL ON text, and as every scroll the recordings send is — and shows a smaller one unscrolled. The pel is rescaled to whole pixels, or whole fractions of one, so a picture drawn in it cannot skew. A packing counter of 0 or above 48, and a first pel outside the field, make the command a null operation, as the standard says.
* **DRCS characters and texture masks** are defined in a buffer of the character field's (or the mask size's) shape, the larger side spanning the unit screen's axis (§6.2.3), and every element takes the colour written into it — on, unless it was written in nominal black.

**Save PNG…** writes the display on screen to an image file, drawn as the record stands once finished — every stage drawn and every colour at rest, whatever moment of the animation is on screen. A presentation record is drawn on its own at 1536 by 1152, the size the receivers share (see above), at the 4:3 aspect of its display area, with no border around it and the text pane left out; **Show display area** is honoured. The name offered is the record's channel, address and version — `Record-000-1A4-v0.png`. The control appears for a drawn record only: an application record is a listing of function descriptors and there is nothing to rasterise.

**Save SVG…** writes the display on screen as an SVG drawing: the same shapes the viewer draws, as vectors, so it scales to any size without losing detail. It plays the presentation as the viewer does, using SMIL animation that a web browser runs with no script. Each stage appears at the moment it did. A figure drawn in a blinking or changing colour-map entry changes with the entry, loops included, because every figure in that entry is painted from one gradient that the animation drives. A page that does not change comes out as a still drawing. It is drawn at the size **Save PNG…** uses and offered under the same name ending `.svg`, and **Show display area** is honoured. The control appears for a presentation record only.

**Save All PNGs…** writes every drawn record of the catalogue in one pass, into a folder chosen once. Each image is exactly what **Save PNG…** would have written with that record on screen, under the same name; application records are listings rather than pictures and are skipped, just as the single save is not offered for them. A progress dialogue says how far the batch has got and cancelling it keeps what was already written. The button stands whenever the catalogue holds anything drawn, even while a listing is on screen.

**Save All SVGs…** does the same for the SVG drawings: every presentation record of the catalogue, each exactly what **Save SVG…** would have written with that record on screen — animated, at the same size, under the same name ending `.svg` — into a folder chosen once, with the same progress dialogue.

**Option keys** play a page that was made to be played. ANSI X3.110 lets a page link the macros it defines to a receiver's keys (§5.5: "Any macro ... may be linked to a user input mechanism, such as a function key, to allow its execution ... to be activated by the user"), starting at 2/0 (Table D1 item 7), and the NABTS service's option function did it with the digit keys — "a key linked to a macro that moves the drawing point a relative distance and then draws an object at the new position ... can be used to move an object around the screen", as RCA described it. A game made for such decoders is a page of this kind: it defines macros 2/0 to 2/9, never runs them itself, and tells the viewer to "Press Option 1-9". A page that defines macros on the digits it never runs is marked **Game: keypad** in the list, and while it is on screen a keypad stands beside the drawing — the digits laid out as on a set-top keypad, those the page links enabled. Pressing one, or typing the digit while the drawing has the focus, runs macro 2/n from the state the page and every key before it left — the drawing point, the colours selected, what is on screen — exactly as a decoder ran it, and the page is redrawn with what the key drew. With **Receiver pace** or **TU-2000x pace** on, what the key draws is seen being drawn. **Reset game** shows the page as it was sent again; so does moving to another record. Where the viewer also takes a page number on its keypad, a **Play** / **Page** switch over the keys chooses which the digits do, on **Play** for a page that plays. The keys pressed are kept by the viewer and replayed from the page each time, so a game in progress survives a change of **Receiver** or of the pace boxes, redrawn the new way. The Panasonic TU-2000x links its keys the same way — a number then **#** runs the macro with that number — and runs the macro with the cursor off, as here; the Norpak TTX 650 links none. Nothing a run exports changes: the report marks such a page "plays in the viewer" and draws it as sent.

**Reconstruct lost data** rebuilds the bytes the recording never received, and puts right the bytes it received wrong where parity proves them wrong. It is off unless you turn it on: what the viewer shows to begin with is what the recording carried, because that is the one reading nobody has to take on trust.

A packet the recording lost took a stretch of every record it carried a block of, and the recovery can only leave the stretch as the filler of a lost packet — bytes that NAPLPS reads as nothing (§6.1.6.1). So the command the loss cut is read as carrying on with the operands of whatever came after it, and a colour, a DOMAIN or a shift the loss took is simply not there: one lost operand can repaint the rest of the page. On most recordings that is an occasional packet. Where a recording lost the packets of one line on every field, it is the same stretch of every record, every day — see **Packets the tape never had** below — and most of what goes wrong on its pages.

With this on, each lost stretch goes through two steps.

* **Filled from another record.** A service built its pages from templates — the same palette set-up, logo, frame and map outline on page after page and day after day — so a stretch one record lost very often stands whole in another: another page of this recording, or the same page in another recording that did not lose it. Where the bytes on both sides of the stretch occur in such a record exactly the stretch's length apart, what lies between them there is copied in. It is done only where the agreement is long enough to vouch for it (at least 56 bytes across the two sides, neither side a run of padding or one repeated byte), and only where every record that agrees as well offers the same bytes — or where one set of bytes is offered by at least ten times as many records as any other and by at least two, with 32 bytes of agreement: a stretch several pages share turns up in a dozen records and a stray reading of it in one. Tested on recordings that lost nothing, with a regular loss punched in, that settles about two in five of the stretches the other records disagree about, nearly all of them exactly as sent. The records drawn on are this recording's own and those of the reference recordings the **reference_records** parameter names.
* **A lost shift put back.** Where nothing can vouch for a stretch, nothing is put in its place, and what arrived around it is read as a receiver would read it with those bytes gone. The one thing put back is a shift between text and drawing commands: where the bytes after the loss read far more like text than like drawing commands, or the other way round — judged by the service's own habits, learned from the records this recording and its references carried whole — the shift the loss took goes back at the end of the stretch. Holding back the operands a loss orphaned, rather than drawing them as part of the command before it, was tried as well, and on the holdout below it made pages slightly worse.

Bytes that arrived failing the odd parity CEA-516 §3.3 gives every data byte of a record are known to be wrong: the vote had no copy with a clean value for them. Before the lost stretches are rebuilt, each such byte — every record's, whether or not it lost anything — is looked up the same way a lost stretch is, and where another record has the same bytes all round it, what that record has in its place is put in, provided it passes its own parity. Damage comes in bursts, so the other wrong bytes near it are stepped over rather than ending the agreement, but a byte that passed its parity and differs still ends it. Nothing else that arrived is changed.

Measured by damaging recordings that lost little — one byte in a hundred of those that arrived clean given one wrong bit, singly and in bursts of up to four — with other recordings of the service as references, nine in ten of the damaged bytes or more are put right, and almost no correction is wrong. On a recording as recovered, a byte received failing parity is put right where another recording agrees with its stretch closely enough; the rest stay as received.

Measured on complete recordings with a regular loss punched into every record and other complete recordings as references: two thirds of the lost stretches are filled, and nearly every fill is byte for byte what was sent. Pages drawn at 256 x 200 exactly as sent go from a few in a hundred to about a third, and the pixels wrong on an average page fall by two thirds. How much comes back depends on how close in time the references are: recordings of the same days give back nearly whole pages, references years apart much less. With only the recording's own records to draw on — which lost their stretches in the same places — almost nothing can be filled.

Pages drawn from rebuilt or corrected bytes are marked `~` beside their address in the list. The line above the message panel says what was done to the page in front of you — how many bytes the recording lost, how many were rebuilt and from which recordings (the first three by name, and how many more), how many shifts were put back, and how many of the bytes it received failing parity were corrected — and the message panel says how widely the catalogue was touched.

None of this touches what a run exports: the packet stream, the record files and the report carry the recording's own bytes.

**Caption track** switches the right-hand pane to the recording's captioning: the captions as they arrived (see **Captions** under **What it does**), in transmission order, each cue running until the next replaces it. §7.3.10 carries captioning as a run of records that each replace the last, so the cues — not the individual records — are what the service actually says, and a caption repeated unchanged under a new version is one cue rather than two. The caption service is not listed record by record: it is the one **Caption track** item of the list. The control is only enabled on a recording that carried captioning, and the line above the list says which channels and addresses those were.

## Parameters

### output_path (file path)
Path to the output packet stream. The `.t33` extension is appended if absent.

Optional. Leave it empty and the run decodes exactly as it would but writes no file, which is what to do when the records themselves are what you are after — the **NABTS Records** tool is filled either way. `write_report`, `export_records` and `export_captions` all write beside the packet stream, so they need a path and the run is refused if any of them is enabled without one.

### first_vbi_line (integer)
First candidate field line probed, 1-based, applied to both fields. Default 10.

### last_vbi_line (integer)
Last candidate field line probed, 1-based, applied to both fields. Default 20.

Together these give the window CEA-516 §1.1.1 and ITU-R BT.653 §2 define — broadcast lines 10 to 21 of field 1 and 273 to 284 of field 2 — short of line 21 itself. Line 21 of both fields is the caption line (47 CFR 73.682(a)(22), 15.119), and its EIA-608 is not rejected as reliably as its lack of a framing code would suggest: on captioned recordings it gives packets now and then, and read alone it gives packets almost none of which have a whole prefix, and no record — noise that went into group reassembly beside the service's packets. A service that did put NABTS on line 21 is read by setting `last_vbi_line` to 21. CEA-516 §1.2 also permits full-field transmission on lines 10 to 262, which this stage does not cover; Norpak's encoders offered lines 10 to 25 of each field for NABTS, and full-field insertion besides.

Narrowing the window to the lines a service actually uses is worth doing when you know them. It keeps noise that happened to pass a framing code out of the packet stream, and — because the data-phase tracker pools its locks over every line of the window — it can be the difference between the phase pin engaging and not. On the CBS ExtraVision reference capture, reading the full window yields 2460 packets against 2288 on the four lines the service uses; the 172 extra are noise, every one of them refused by the group header check. The records a user browses come out the same either way.

### keep_empty_packets (boolean)
Emit a whole zero packet for every candidate line that yielded nothing, so packet position in the file maps 1:1 to (frame, field, line). Off by default, which writes only the packets that were recovered.

### detector (string)
How data bits are recovered from each line.

* **Threshold** slices at interpolated bit centres after locking to the clock run-in. Cheapest and exact on a clean signal; suits discs and direct captures.
* **MLSE** fits the recording's frequency response to the known 24-bit start of each line and finds the bit sequence that response would most likely have produced. This is what recovers data from tape, where the limited bandwidth smears each bit into its neighbours and no bit-centre threshold can work. Each reading then refits that response to the whole packet it has read and reads it again. On a tape played through a recorder's own electronics, and through a capture card after them, the response also rings for about a microsecond: it undershoots by a few per cent of the data step three to six bit periods after its peak, beyond the five bits the response is fitted over, and the alternating run-in cannot measure it. So up to three more refits follow, while the bits keep changing, that fit the response to the four bits before those five as well, taking those bits from the decisions each path through the trellis has already made rather than enlarging the trellis — delayed decision-feedback sequence estimation. A refit fitted to its own decisions can also settle on a wrong reading of the packet's head, where it has least to go on, so one is kept only while the five Hamming-protected prefix bytes it reads arrive no worse than in the reading before it: no more of them past correction, then no more needing it. On a card dump where the ringing put the first prefix byte wrong on half the packets, the packets whose every byte checks out rise from a few in a hundred to most of them (see **What a marginal tape looks like**), and across tapes generally record bytes failing parity fall by about two thirds. Without the guard, a tape can lose half its packets to a first prefix byte read two bits wrong. The fit cannot tell the true start of the clock run-in from a shift of it by a whole bit or two — the run-in repeats every two bits and the fitted response absorbs the difference — so the packet is read at the five shifts whose fits explain the line's start best, and the reading kept is the one whose prefix bytes arrive as sent and whose bit decisions were surest. Because the fit assumes the synchronization sequence rather than finding it, a reading whose prefix needed Hamming correction then reads the sequence back with a channel fitted to its payload alone. It is kept only if the framing code comes back within the one wrong bit CEA-516 §2.2.3 allows for and the clock run-in comes back still alternating. A reading whose five prefix bytes all arrived as sent is kept without it: a line carrying no packet does that about once in a million. That is what stops most of the test signals and captions on neighbouring VBI lines from being read as packets. Tens of times the work per line of the threshold detector, most of it in the five readings; modelling the ringing costs the lines MLSE reads two to three times as much again. On an x86-64 processor with AVX2 the detector works four of its numbers at a time — the branches of two trellis states, the preamble fits of four candidate phases — which takes about a third off its time; what it reads is the same to the bit on any processor.
* **Automatic** (default) tries Threshold first and falls back to MLSE on lines it could not lock, and on lines it locked but read with an eye margin too small to trust — the band between a clean source and a tape, where the threshold detector still finds the clock run-in but its bit-centre samples sit close to the slicing level. A clean source pays nothing extra.

A NABTS packet read by the MLSE detector is then held to its own checks, where it carries them. A packet whose structure byte announces the one-byte suffix (CEA-516 §3.4, PS b8,b6 = 0,1) ends in a longitudinal parity check over everything after its prefix, and in a broadcast teletext data group every data byte carries odd parity (§3.3): together, a product code. The structure byte is believed only where it arrived as sent: three bits wrong in a Hamming 8/4 byte decode as another value with one bit corrected, and on a service that sends no suffix, a misread one announces a check that was never sent. The detector's characteristic error on tape is a transition read a bit early or late — 1010 read as 0101 — and inside one byte that keeps the byte's parity. On VHS recordings a few packets in a hundred arrive with every data byte passing parity and the check failing, and on worn EP tapes one in ten or more; a byte read so can draw a line across a page, or move a corner of a figure off the screen and lose the whole shape. Such a packet gets two more looks.

* It is read again along its own bit timing. A tape's speed varies within a line: fitted against their own bits, a recording's packets have their last bits a fraction of a sample (more on damaged ones) off where the nominal clock puts them relative to their first, while the bits between follow a straight line to within the measurement's noise. So the timing is measured against the channel's prediction from the bits decided, 16 bits at a time, a straight line is fitted through it, the line is read again along it and the channel refitted. As with the refits, the new reading is kept only if its prefix arrives no worse and no more of its data checks fail, and only if it still passes the gates the first reading passed — a packet structure byte the service can send, and the read-back of the run-in and framing code — so no packet the first reading delivers is lost to the second.
* If it still fails its check or a byte's parity, it is read once more as the most likely bit sequence that passes both: a trellis that carries the running exclusive-or and the byte's parity beside the channel state, with the prefix held as read. That reading is taken when the samples support it nearly as well as the first — within three quarters of a bit's energy where a byte failing parity shows where the error is, within a fifth where only the check failed and the error could be in any byte, because there a wrong choice passes every check afterwards (on a damaged tape most choices beyond a fifth were wrong). A packet sent with a check that does not hold, or damage the samples clearly show, is left as read. The bytes it changed are reported with no confidence, so in the vote a copy of the packet that arrived whole outweighs them.

Measured against the consensus of each packet's other copies, on a service that sends the check the two looks halve the bytes read wrong, take out a large part of those among them that pass parity — the errors no vote can tell from a right byte — and read more packets whole, losing none the first reading delivered. A service that sends no check is read exactly as before: with parity alone to judge by, a second reading put about as many parity-passing errors into right bytes as it took out; and a two-byte suffix (PS b8,b6 = 1,0) is forward error correction, not this check. The detector's time rises most on damaged tapes, by a quarter to three quarters, and hardly at all on clean ones.

A NABTS packet whose reading, checked, still fails a data check — a byte's parity, or the longitudinal check where one is sent — is read once more through a wider channel, where the packet's own channel needs one. Some tape transfers respond to a bit three bit periods before its own sample: fitted against each packet's own bits, some VHS EP recordings respond to it by several per cent of the data step on nearly every packet, where cleaner transfers barely do. No five-bit window holds that, and such tapes lose the same bytes to it in every copy, so no vote of copies wins them back. The wider reading fits a window reaching a bit further ahead, with the eight bits behind it read off each path of a 32-state trellis, refits it while the bits keep changing (three times at most), and is kept only where fewer of the packet's checks fail, its prefix arrives no worse — and as sent where it changed — and its structure byte announces the same suffix and still opens no group. It is taken only where the channel fitted to the packet responds to the bit three periods on by 3 % of the data step or more: elsewhere its extra taps fit noise, and read wide wherever their checks failed, clean transfers came out with more bytes made wrong than put right. Nor is it taken on a packet that opens a data group, whose block is mostly the group's and the record's headers (§4.2.1, §5.2): Hamming 8/4 bytes that a reading made to pass more checks turns into other codewords, so that records read wide were filed under other names, losing pages and listing records that are no page. The bytes the wide reading changed are reported with the packet, and the record layer reads them as bytes that pass their parity because they were read to (see **Records** above and the vote under **Notes**). On the recordings that need it, it takes about a quarter off the record bytes that disagree with other recordings of the same pages and lists no record it did not list before; recordings that do not need it come out as they were. It costs those recordings a few per cent more time, and the rest nothing measurable.

### calibrate_bit_clock (boolean)
Learn the bit clock the recording was sampled at, and read it at that clock. Default: `true`.

The standards hold the bit rate to 25 ppm (System B) or 16 bit/s (System C, CEA-516 §1.3), and a time-base-corrected capture keeps it. A capture card sampling against its own crystal instead reads the tape at whatever speed the transport ran, and the bits arrive a little faster or slower than the standard's rate: on some card transfers a few hundredths of a per cent slower — up to a third of a bit by the end of every packet, which costs the last bytes of the packets that were marginal already.

The clock run-in cannot measure that: eight cycles through a tape channel pin the rate to a couple of per cent, and hundredths of one matter here. So the first packets are read again at a range of trial clocks, and once 400 have been scored the clock at which the most packets arrive with every byte checking out — addressing bytes as codewords, data bytes passing parity — is adopted for the rest of the recording, provided it beats the standard's clock by more than chance allows: three standard deviations of the packets the two clocks disagree on. A detector that reads most packets whole at any clock leaves few for them to disagree on, so where the best trial's lead falls short of that but, growing as a real one does with the square root of the packets scored, would pass by 1,600, the scoring goes on and the test is taken again after 800 and 1,600. On a card dump whose clock runs slow, the slow clocks can lead by less than three standard deviations after 400 packets and pass after 800 or 1,600. A corrected capture scores within noise at every trial, so it keeps the standard's clock, after the first 400 packets or the next. Where a slower clock is adopted, packets arriving wholly undamaged rise by up to a tenth.

The report says which clock the recording was read at, and on how many packets.

### decode_threads (integer)
Threads to recover lines on; 0 (default) uses one per processor. The recovered stream is identical whatever this is set to, so lower it only to leave the machine free for other work. Packets are written from one thread, in order, while the next block of frames is already being decoded on the others; and a VBI Capture Source feeding the sink decodes the capture ahead of the pass on as many decoders as the pass is seen to need — never more than one for every three of these threads — rather than handing frames out one at a time from a single file position. The memory a pass holds grows with this setting: each decoder keeps a few megabytes of the capture decoded ahead of the threads, and each thread keeps the working storage of the MLSE detector from one line to the next, under a megabyte.

### write_report (boolean)
Write the run's diagnostic report next to the packet stream, named after it with a `.txt` extension (`mydata.t33` gives `mydata.t33.txt`). Off by default; the same report is always written to the log at debug level. Needs an output file to sit beside.

Beyond the packet-level recovery profile, the report accounts for every layer above it — how many packets were orphaned rather than placed in a group, how many groups completed, how many record headers were refused, how many linked series were joined, and how many records were catalogued. Those counts are the quickest way to tell a recording that is merely lossy from one that is failing (see below). Its **Idle fill** line counts the data groups of an encoder's test pattern kept from the record layer (see **Encoder idle fill**). Ahead of those counts, its **Other services (not teletext)** block names the addresses that carried an FEC datacast, idle fill, a test sequence or clock packets (see **Services that are not teletext at all**), one line a service; the data groups of a reserved type go beside it as `mydata.t33.other.txt`, as text or as a dump of their bytes.

### export_records (boolean)
Write each teletext record the recording carried as its own file beside the packet stream, named for the channel, record address and version that identify it — `mydata.t33.000-1A4-v2.rec` — with `-2`, `-3` and so on after the version for a second or later page carried under the same identity (see **Records** under **What it does**): `mydata.t33.000-1A4-v2-2.rec`. Off by default; needs an output file to sit beside.

The file holds the record's data as the record dialog reads it: NAPLPS presentation code, or application data for a record of type 2. Where an undamaged copy arrived that is that copy byte for byte; where none ever did, it is the combination of the damaged copies described below. Byte parity is left in place, as it is in the packet stream. This is what to use to take a record to an external NAPLPS tool.

A page salvaged without its header (see **Groups whose first packet was lost**) is written under its listed name, `mydata.t33.000-LOST1-v0.rec`, its lost head as zeros, and the runs of packets salvage could place nowhere as text in `mydata.t33.fragments.txt`. Each decoded datacast's payload is written beside the records too, with the text it holds (see **Datacasts decoded**). Lines found to carry another signal, not NABTS, have their records, datacasts and fragments left unwritten.

The caption service is not written this way: its captions share sixteen versions among them (§7.3.10.1), so no file name could tell them apart. `export_captions` is what carries them.

### export_captions (boolean)
Write the recording's captioning as a SubRip subtitle file beside the packet stream (`mydata.t33` gives `mydata.t33.srt`). Off by default; needs an output file to sit beside.

The cues are the captions the service sent (see **Captions** under **What it does**), in the order they were transmitted, each dated by the first copy of it the recording received and running until the next one replaces it; a caption record with no text is an erase and ends the cue before it, and consecutive captions with the same text are one cue. Cue timing comes from the 59.94 fields per second of SMPTE 170M. The caption flag is what selects them, not the data channel — §7.3.10 leaves a service free to carry captioning on whichever channel it likes. A recording that carried no captioning writes no file.

Colour, positioning and the rest of the NAPLPS presentation are dropped: SRT carries the plain text.

### reference_records (string)
Other recordings of the same service to rebuild from: the packet streams (`.t33`) this stage wrote for them, the record files `export_records` wrote beside those streams, or folders of either, separated by semicolons — `C:\teletext\day1.t33; C:\teletext\day2\`. Empty by default.

They are read at the end of the run, and their records are what the records viewer's **Reconstruct lost data** fills a lost stretch from as well as this recording's own records. Nothing else uses them: they change neither the recovery nor anything a run exports. A record file is read as the record it holds — what that recording's own run made of it, voted from its copies with the line each copy came off and how sure the detector was of each byte behind it — and named for the recording it came from: the folder a run's `out.t33` sits in, or the stream's own name. A packet stream is replayed through the same reassembly and vote as the recording's own packets, without those line positions and confidences, which on a long recording takes minutes (its record files are read in a moment), so a folder stands for the record files in it and for each packet stream in it whose records were not exported beside it. A record file does not say what type of record it holds, so an application record's data is read along with the pages'; a byte its recording never received is the 0x00 a lost packet left, and is read as lost. This run's own stream and records are skipped if they are among them, and a path that cannot be read is reported and passed over rather than failing the run. The report's **References** line says how many records were read from how many streams.

The best references are recordings of the same service whose bytes can be trusted, and a recording that lost packets of its own helps too: recordings that all lost the same packet positions still hold the shared templates at different offsets on their pages, so a stretch one lost another often kept. A recording whose received bytes are often wrong is a poor one, since what it holds in a stretch is copied as it stands: filled from worn EP tapes, a few bytes in a hundred came out wrong, against about one in a thousand filled from recordings whose received bytes fail parity at most once in a thousand.

## What a marginal tape looks like

NABTS asks much more of a recording than World System Teletext does, and it is worth knowing what the failure looks like so a bad tape is not mistaken for a bad decode.

A WST page is a grid of characters, each byte independent and parity-coded, so damage stays where it lands — a corrupted byte is one wrong character. A NABTS page is a **stateful byte stream**: bytes are opcodes, operand counts and coordinates, so one wrong byte changes how the several after it are read. Damage propagates, and a page degrades into overlaid or displaced nonsense rather than into a page with typos.

Two recordings bracket the range, decoded end to end at identical settings:

| | a VHS **SP** recording | a VHS **EP** recording |
|---|---|---|
| decision confidence | 0.55 | **0.22** |
| record bytes failing odd parity | 0.02 % | **7.10 %** |
| packets orphaned rather than placed in a group | 0.09 % | **62 %** |
| record headers refused | 1 in 7736 groups | **866 in 2824** |
| linked record series joined | 1246 | **0** |

The SP recording browses as a working service. The EP recording catalogues 239 records and draws 212 of them, and almost all of them are unreadable. The reason is in the first row: a World System Teletext recording read as NABTS — that is, pure noise fitted by the MLSE detector — comes through at a mean decision confidence of 0.21. The EP tape sits at 0.22. Its bit decisions are at the noise floor, and no amount of decoding recovers a page from that.

So: **mean decision confidence in the report is the number to read first.** Around 0.5 and above, expect readable pages. Approaching 0.2, the recording is at the limit of what can be detected at all, and a better transfer — or a copy recorded at a longer-playing speed's expense — is the only thing that will help.

Both figures above were measured before repeated copies of a record were combined. Combining them changes what a marginal tape yields, and changes what the report means. A later EP transfer measuring 0.36 mean confidence — above the 0.22 of the table, below the 0.5 that reads cleanly — decoded end to end as:

| the service's channel | one copy kept | copies combined |
|---|---|---|
| record bytes failing odd parity | 2.53 % | **0.67 %** |
| record length | short by a third | as the group header declares |
| positions no copy ever received | — | 14.5 %, left as NUL |

Two things are worth taking from that. Damage among the bytes that did arrive falls by about three quarters, because the copies disagree only where they were damaged. And the records come out at their true length: a copy that lost packets used to close up over the hole, which moved every byte after it and is what turned a page into overlaid nonsense. What replaces the shortfall is honest — positions nothing ever arrived for, left as a control with no presentation effect.

What it does not do is invent data. A third of that recording's record positions were never received on any pass, and no vote recovers those. Nor does it move the bottom of the range: at 0.2 the bit decisions are the detector fitting noise, the copies disagree everywhere rather than in a few places, and there is nothing for a vote to find.

Part of that bottom, though, was the detector's own. A recorder's playback electronics, and a capture card after them, ring for about a microsecond after each bit: the response undershoots by a few per cent of the data step three to six bit periods after its peak, outside the five bits the detector's channel model spanned. Left out of the model, the ringing lands where a run of ones ends, and every NABTS packet ends one in the same place — the framing code's last three bits — so the first casualty was the first prefix byte. On a capture card's dump of one EP tape the channel address read wrong on nearly half of the packets, and the packets took their groups and records with them. With the ringing modelled (see **detector**), three transfers of that tape decode as:

| one EP tape | capture card dump | vhs-decode | TBC crop |
|---|---|---|---|
| mean decision confidence | 0.19 → 0.28 | 0.24 → 0.27 | 0.22 → 0.28 |
| packets whose every byte checks out | 4 % → 71 % | 42 % → 73 % | 26 % → 75 % |
| data groups completed | 676 → 1247 | 880 → 1195 | 1807 → 2856 |
| record bytes agreeing with the vhs-decode transfer | 71.8 % → 99.5 % | — | 98.7 % → 99.9 % |

The card dump's index page, which had drawn as a field of stray characters, now draws as the vhs-decode transfer's does. Mean confidence on these tapes stays below 0.3, so read it as a ranking of recordings rather than a verdict on one: the floor is lower than the table at the top of this section put it.

### Packets the tape never had

A packet a recording lost is usually lost to noise: a different packet on each pass of the carousel, so the vote across a record's copies fills it in. Some recordings lose a packet the vote cannot help with, because no copy ever had it.

A service can send each data group a few packets to a field on consecutive lines, starting each group on the same line. Where the signal recorded carries a test signal on one of those lines instead of data — a multiburst laid over it before the tape — that packet of every field was never recorded. The continuity index shows the packets were transmitted — it steps by two where one is missing — and the gap falls on the same data blocks of every record, every day: with three packets a field and the third lost, blocks 2, 5, 8 and so on of each group, 27 bytes of every 81, about one byte in six of everything the service sent. Recordings of the same pages on different days lose the same bytes.

No setting of the recovery can bring those bytes back, since they are not on the tape. The report's **Per VBI line** table shows it plainly — data on the lines around it, a burst on the test signal's line that never decodes — and so do the record files, as 27-byte runs of zeros at 81-byte spacing. **Reconstruct lost data** in the records viewer is what can help: point **reference_records** at the other recordings of the service, and pages whose templates survive elsewhere come back.

### Addresses the recording named but the service never sent

A damaged tape does not only lose records — it invents them, and the invention is convincing.

Every digit of the identity CEA-516 §5.2.1 gives a record — the three packet-address digits, the record address, the version — arrives in its own Hamming 8/4 byte. That code has minimum distance 4 (ETSI EN 300 706 §8.2), so it corrects one bit error and detects two, but a burst of **three** lands inside a neighbouring codeword's correction sphere and is resolved there silently, with no indication that anything was guessed at. On a band-limited recording that is the ordinary error rather than the exotic one: the MLSE detector's characteristic failure is a run of alternating bit inversions, and the codeword for digit 0 is itself an alternating pattern, so digit 0 is carried onto digit 7 over and over.

The damage that does is not to the record. The record still decodes; it is simply filed under an address the service never transmitted, where it sits in the catalogue beside the real one holding the same page. The reference ExtraVision EP capture reports 1389 distinct identities, of which only 184 were ever received as transmitted; the rest are that.

So the run counts, per record, how often its identity arrived **as transmitted** rather than corrected into shape, and weighs every identity that never once did against its content:

* where it carries the page of an attested identity, it is a misreading of that one: its copies join that record's vote — they are that record's bytes, and they were received — and its appearances are added to it. The two are compared by what their copies combine to, over the bytes both received with their parity intact — at least 48 of them — at the slip that agrees best. A copy from a damaged tape is mostly holes, and compared byte for byte over the longer of two copies, holes and all, as it was, two pages agreed where both had lost their bytes and a page's own misread copies matched nothing: a page's copies that arrived under a misread channel were listed as a record of their own, and identities misread onto one channel were folded into one another and voted into one record.
* where it recurred under that one identity with a page no other identity carries, and at least two of its copies are copies of each other (or one arrived intact), it is a record whose address the tape corrupts the same way every time. A tape can deliver a run of pages fifty to eighty times each with an address digit that is corrected on every one of them, where random damage lands on a different address each time it strikes. It is kept, and marked **unconfirmed** in the list. Copies of several pages misread onto one name are not kept that way: each agrees with the record they make up between them, but not with one another.
* a record seen once is too little to go on: it is folded into the one attested identity a digit away, or removed where there are several or none.

Neither fold is made into a page the record is not. Two pages built on one template agree on it as a page's misread copies do (see **Records** above), so a record whose content is another page on its neighbour's layout is not folded into it by content, and a single sighting of one is removed rather than voted into its neighbour — unless its record header says otherwise. Each Hamming byte of the header is a digit of the identity or decides how the rest are read, and a header that arrived as codewords throughout, with only the packet address corrected, on the data channel most of the recording's attested identities are on, names a page the service sent under that address and version. Such a record is kept and listed, marked unconfirmed, where it would otherwise be removed. A second page on a shared template, seen once with every byte of its record header a codeword and its packet address corrected into the service's channel, is so listed beside the page whose template it shares rather than voted into it byte by byte. An identity one of whose contents was named as transmitted is the service's already, and another content of it, seen once and matching none, is not kept this way.

A version is a Hamming 8/4 digit of the identity like the others, and §5.2.7.2 has a service change it when it revises a record, the revision then replacing the version before it. So a version seen only inside the span of another version of the same address, at most a twentieth as often (that one seen at least 20 times), whose bytes agree with that version's on nine in ten of those both received, is that version with its version digit misread, and is folded into it even where its header arrived as codewords and so names it as transmitted. Listed on its own, such a version is a page drawn from damaged sightings — a byte misread as a DOMAIN (two bits swapped, parity intact) can set a logical pel a hundred pixels tall and smear the page. A revision is seen after the version it replaced, and a carousel's versions are seen about as often as one another, so neither is taken for one.

The record type is a Hamming 8/4 byte of the header too (§5.2.2), and only types 0 to 3 are defined: 4 to 15 are reserved, no service sent one, and both decoders of the day refuse a header that carries one. So a copy whose type reads as reserved did not name its record as transmitted whatever its other bytes say, a record's type is the one most of its appearances carried, as its flags are (see below), and a record whose appearances mostly read a reserved type is never kept as a page of its own — it is folded into the page its bytes are, or removed. A damaged tape can read one digit as another in every Hamming byte, its type bytes among them; listed by their longest copy's type, such records would be of a reserved type, though most of them are pages of type 0.

Across the recordings this lists 94 records under a name no appearance named as transmitted, against 288 before, and none of them is the page of a record listed under its own name, where 139 were.

A packet address is Hamming 8/4 too, and four wrong bits carry one codeword exactly onto another, so a packet can arrive misaddressed with its address as transmitted. Where it is a page's synchronizing packet, it opens a group on a data channel the service never used, under the page's own record header, and the group takes in whatever else is misaddressed there until its block count is reached: blocks of other pages, or of the page, each at the wrong offset. A record filed so holds blocks each verbatim from another page at another offset. So a record on a data channel other than the one most of the recording's attested identities are on, none of whose copies arrived intact, whose address and version a page of that channel carries — seen four times as often or more — is removed, named as transmitted or not. Such records are seen once to three times, against tens or hundreds of sightings of their namesakes. A service's records on a second channel of its own, such as caption records, carry no address of its pages and stay.

The run's report says how many identities were folded, kept and dropped, and how many records were removed as misaddressed; the records viewer says across its foot how many were folded, kept and dropped, and how many were removed as misaddressed, so a list that differs from an earlier run's is explained rather than mysterious.

On an undamaged source every byte arrives as transmitted, the pass finds nothing, and nothing changes. The one case it declines outright is a recording where *no* identity was ever attested: there is then no baseline to judge the rest against, and the catalogue is left exactly as recovered. Every record of such a recording is listed marked **unconfirmed**, and the foot of the window says why.

### Lines that carry another signal

A line can carry NABTS's run-in and framing code without carrying NABTS: another service on NABTS's physical layer, or a datacast whose bytes behind the framing code are uniformly random. Hamming correction lets a little of such a signal through as packets, from which a catalogue of noise could be made, so the report says how many of the packets written arrived with all five prefix bytes whole (CEA-516 §3.2.1). A recording of NABTS gives 70 % or more, worn EP tapes and card dumps included; lines that carry another signal give a fraction of one per cent. Where fewer than a tenth of at least 200 packets arrived whole, the report and the foot of the records viewer say the lines carry another signal, not NABTS, and nothing is listed or exported from them; the packet stream is written as recovered.

A single line can carry another signal too, among lines that carry NABTS. World System Teletext on 525 lines shares NABTS's bit rate, clock run-in, lines and levels, and differs in two bits of the framing code; the MLSE detector accepts a line whose samples fit NABTS's code within a margin of WST's, so that a genuine line damaged in those two bits is not lost, and on a band-limited tape whose smearing leaves the two codes fitting a WST line about equally, its rows pass inside the same margin as NABTS packets on made-up channels. So each line's run of packets is judged: once a line has yielded 64 of them, a line where a fifth or more preferred WST's code is WST's (a line of NABTS prefers it on well under one packet in a hundred, a WST line on about half), and a line where fewer than a tenth of the prefixes arrived whole carries some other signal; every packet such a line yields is refused, and the report's **Packets** line counts them. Until a line is judged, a packet preferring WST's code is refused on its own account. The **Per VBI line** table numbers the lines from 1, as the line window does.

The classification flags of §5.2.7 are bits of the same header bytes and fail the same way. One copy of a page arriving with its caption flag misread would otherwise put that page's text in the caption track, and one with its support-record flag misread would make an ordinary page the channel's Support Record. So a record's flags are not taken from any one copy: a flag is set when most of the appearances that named the record as transmitted had it set, or, on a record no appearance ever attested, most of its appearances of any kind. On the NBC EP transfer no caption flag was ever received as transmitted — every one was a single misread copy of an ordinary page — and the caption track is now empty. On the ExtraVision SP capture, whose caption channel carries the flag on every copy, the captions are unchanged.

The caption service is taken from the arrivals rather than from voted flags (see **Captions** under **What it does**), and the same caution holds there: an arrival whose header had to be corrected joins the caption service only where its record type reads non-cyclic as well, which is how captioning is sent (§5.2.2.3), or it comes from an address the caption service is already using. A misread caption flag on a cyclic page so leaves the page in the catalogue and the caption track empty.

### Continuity indices that could not be true

The continuity index (§3.2.4) is how a group learns that packets went missing: it counts the channel's packets modulo 16, so a gap in it is the number lost. It is a Hamming 8/4 byte, and a burst that resolves it into a neighbouring codeword makes it read as some other number — most destructively as the previous packet's own index, which by the arithmetic is fifteen packets lost. Taken at its word that opens a fifteen-packet hole in the group and puts every byte after it fifteen packets late, so the copy of the record agrees with the others up to that point and with nothing after it.

On the NBC EP transfer that is not rare. Continuity index 14 is regularly received as a codeword three bits from its own that corrects to 13, and gaps of fourteen and fifteen packets turned up three times as often as gaps of twelve and thirteen, and almost all of them arrived with fewer lines gone by than they claimed packets lost.

That is the check the run makes. A packet travels on a line, so no more packets can have been lost since a group's last one than there have been lines since — counting the lines that yielded no packet, the lines that yielded a packet of any channel, and none of the lines the pass has learnt never carry data (see **What it does**) unless the continuity index has shown packets routinely lost there. An index claiming more than that was misread. Where no line went by since the group's last packet, none of its packets can have been lost there, and the packet is simply the next. Otherwise some loss was possible and how much cannot be told, so the rest of the group is left unplaced — its bytes counted as lost rather than put in a place that might be wrong: the record's other copies and other recordings can put back bytes known to be missing, and nothing can tell a byte in the wrong place from a right one. Measured against other recordings of the same pages, this leaves far fewer bytes wrong in the vote than reading the damaged index as whichever possible loss its byte lies nearest to, for a tenth of one per cent of the bytes it gets right; leaving the rest of the group unplaced even where no line went by gets fewer right and more wrong. The report's data group section says how often an index was misread.

On the NBC transfer this put half as many again of the copies' bytes back where they belong, cut the byte positions the vote could not settle from 1616 to 520, and turned pages that had drawn as fragments into readable ones. On the ExtraVision SP capture, recorded at a speed that rarely produces the burst, it acted 14 times in 293 575 packets.

An index can mislead the other way as well. It counts modulo 16, so it reads eighteen packets lost as two, and where a tape loses a field of every frame, or runs of frames with nothing on them at all, a whole index's worth of packets can go by unseen: the rest of a group and the start of the next, its synchronizing packet among them. Read as the smaller loss, the next record's packets were taken for this one's. On a capture that reads one field in two for a stretch, loses whole runs of frames, or breaks off for thousands of frames with no data at all, a page can be listed a second time as a single copy that ran on into the page sent after it. So the empty lines that went by are set against the larger reading. How many of the group's packets they could have carried is estimated from the share of the lines that carry data its blocks have taken since it began — nearly all of them on a channel that fills its lines, as a teletext service does, few on one whose packets come seldom, such as an encoder's idle fill — and where that accounts for sixteen more than the index reads, how many were lost cannot be told and the rest of the group is left unplaced, as after a misread index. A line the pass reads only on its periodic look at the whole window, never seen to carry data, is not counted, and a packet whose prefix failed is, since whose it was cannot be told. A copy left unplaced so is never one that arrived whole, and against other recordings of the same pages the bytes right and wrong are unchanged. The report's data group section says how often it happened.

A line the pass has stopped reading is usually one the service never used, and there the tight count is what catches a misread index. But a tape can lay a test signal over lines the service did transmit on. A service sending four packets a field on consecutive lines, on a tape that lost one of those lines to a test signal on every field and another on some (see **Packets the tape never had** above), leaves the pass to learn that the lost line never yields a packet and to stop reading it, yet the continuity index still counts the packets it carried on air. Left out, those losses read as misread indices on nearly every field, and the group closed up over the missing block instead of holding it open — so the same record came out with its bytes in two different places, depending on which fields its copies crossed.

The index itself says where this happens. Two consecutive packets of a channel step it by one more than the packets sent between them, so every pair of positions — the line and field of one packet and of the channel's next — collects the losses its steps show. A loss seen at least three times and on more than half of the steps between the same two positions is routine there, and the group is told of that many lines before the packet arrives (never more than the window has between the two). On a tape that lost a line to a test signal, the steps show a packet lost between the lines either side of it; on a tape whose test signal is on a line the service never sent on, every routine loss falls on lines the pass reads, and nothing changes. The report's **Active lines** entry lists the routine losses the groups were told of.

On a tape that loses a line this way, the continuity indices read as misread fall from hundreds of thousands to about a thousand, three times as many data groups complete, and pages that had come out cut short and closed up read whole; two transfers of one such tape agree on nearly all the record bytes both carry, where they agreed on well under two thirds.

## Notes

* NTSC and PAL-M sources are accepted. A 625-line source is reported as an error: CEA-516 §1.1.1 specifies NABTS on the 525-line NTSC signal, and the stage's line window and timing follow it. Norpak's encoders could also insert NABTS into 625-line video, but no such recording is known.
* NABTS carried more than teletext. Recordings of public stations of the 1990s carry datacasts in NABTS packets protected by the bundle code RFC 2728 later standardized for IP over the VBI — a Reed-Solomon row code over 16-packet bundles — and a station's NABTS lines can share the VBI with programme-guide data and other VBI data services that use other framing codes. Those datacasts are framed services (see **Files the datacasts carried**): not enciphered but sent under one fixed pad, and what they carry — web pages, pictures, programs, documents and stock quotes — is decoded and unpacked. No IP-over-VBI or ATVEF enhanced-TV data (ATVEF Transport B on packet addresses 4B0 to 4BF) has been found in the recordings so far.
* Packet address F00 is where Norpak's encoders put their bit-error-test fill "when the output would otherwise be idle" — NABTS with byte sync E7, always on F00 — so a channel F00 of meaningless data is an inserter's idle fill rather than a service.
* Empty VBI lines are cheap to probe under every detector: a line that never rises meaningfully above blanking is rejected before any detection runs.
* Nothing is corrected in the packet stream. The prefix bytes are written as recovered and left to their own Hamming coding, and the data block to its own byte parity and longitudinal check byte. The **Reconstruct lost data** control in the records viewer does not change this: it rebuilds the *reading* of a record, never the bytes any file receives.
* Byte parity is not used to repair damaged bytes **in the packet stream**, as it is for World System Teletext. CEA-516 §3.3 gives the data block odd parity only when its data group is of type 0, and a single packet does not say which type its group is — so at the packet layer a byte that fails parity is not known to be damaged. Where a packet carries the longitudinal check byte of §3.4, that byte and the per-byte parity do form a product code, and a single-bit error in the block is located and corrected. Whether a service sends it is the service's choice: ExtraVision does and 768 blocks were mended on the reference capture, NBC does not and none were.
* By the time a record is assembled the group type **is** known — §4.3 makes a type-zero group the only one carrying a teletext record, and everything else has already been set aside — so at that layer every byte is known to be parity-coded and one that fails the check is known to be corrupt. That is what gates the vote described next.
* A byte that still fails its parity after the vote — and, with **Reconstruct lost data** on, after correction from another recording — is drawn as its seven bits. The receivers of the day part here, and neither way carries over to a recovery: the TTX 650 blanks a whole block that fails and draws nothing past it until a later copy fills it (CEA-516 §8.5.2.2.2), which the vote across copies already does better; the TU-2000x draws a failing character as a checkerboard, skips a failing control and abandons a command whose operand fails. Keeping the byte keeps every operand after it where it was sent, where dropping it would move them all, and a wrong value moves one point where a missing one shifts the rest of the figure. The line under the page says how many such bytes it holds.
* Where no copy of a record ever arrives undamaged, the damaged copies are **combined** rather than one of them chosen. A carousel (§7.1.2) brings each record round for the length of the recording, and the copies differ only where they were damaged, so a vote across them recovers bytes that no single copy has right. The vote is per byte position: a parity-clean candidate beats a corrupt one however often the corrupt one arrived, and a position every copy damaged falls back to the best of a bad set. The record dialog says how many copies a record was combined from. The moment an undamaged copy arrives it is used as it stands and the copies held for the vote are dropped.
* Above parity, a byte whose data block the suffix check vouched for — its longitudinal check of §3.4 passed as received, or the product code put its one wrong bit right, and every byte of the block has the odd parity §3.3 requires — beats every byte of a block the check failed, however many copies agree on that one. Parity sees an odd number of wrong bits in a byte and nothing else, and the commonest damage a VHS recording does is two neighbouring bits of one byte, which parity passes; nor is the damage random — the same bits are misread the same way copy after copy — so copies of a failed block that agree are no evidence against a copy the check passed. The check vouches for a block as received, though, not for the record it was filed under or where its bytes landed, so only a copy that agrees with nine bytes in ten of what the copies mostly say (by parity and weight alone) is believed this way; a copy slipped by a misread header, one of another record, or one of an earlier version of the page, votes as before. Where the check passed more than one value, the vouched copies alone weigh them. The combined record keeps the mark: each byte the vote settled on a value the check vouched for says so, for what reads the record afterwards — the test for two pages on one layout among them. On a service that sends the check on every packet, this made independent recordings of the same pages agree more in every comparison and less in none. A service that sends no check is read as before.
* A block whose longitudinal check passes while a byte fails its parity is damaged, not clean: two wrong bits down the same bit column cancel in the longitudinal check, and parity still sees each byte they fell in. In a type-zero group such a block counts as damaged, so no copy holding it is taken as undamaged, and its bytes are not vouched for.
* A byte the detector's wide reading changed (see `detector`) is never vouched for, though its block's check may pass — the reading was taken because the checks pass under it — but votes among the parity-clean bytes by its weight: the wide reading is the better reading of the tapes it is taken on, and the errors it mends are the ones every copy shares. Ranked below every byte a copy received passing its parity instead, it left more bytes wrong against the pages' content, and split no page the fewer. Where the value the vote settles on is held only as the wide reading made it, the record's mask says so, and the comparisons made of the record afterwards read it as they read the copy.
* Among candidates of equal standing each copy is weighted by how sure the detector was of its byte, rather than counting one vote apiece, so a value read cleanly outweighs more copies of one the MLSE detector nearly decided the other way. The threshold detector weighs each byte by its eye margin — how far the least certain of its eight bit-centre samples sat from the slicing level — so a byte read with a closed eye weighs less than one read cleanly, on the same scale the MLSE detector's margins use. A tie goes to the most recent copy.

  The weighting earns its keep where copies are few. With two copies disagreeing there is no majority to find at all, and the choice would otherwise fall to whichever arrived last; with eight or more the majority is usually decisive on its own. On the NBC EP transfer, which averages around eight copies per record, weighting changed no byte of the result — the parity gate and the count between them had already settled every position.
* Only copies that line up position for position take part. A group that lost packets (§3.2.4) holds each hole open at the width the lost blocks would have filled, so every byte after it stays at its offset and the copy votes over the bytes it did receive. A group can also close up over a packet it lost without the continuity index showing it, and then nothing marks the copy: it agrees with the others up to the lost block and holds the next one from there on, and where every other copy lost a block — a tape that loses one line's packets every field does — it is the only copy holding a byte there, and the record held the next block in its place: text that reads "Press 16 for Joe MontPress 16 for", where a recording of the same page whole shows the block belongs 27 bytes further on. So where fewer than half the copies that reach a position hold a byte, a copy that, at the eight nearest positions on one side that most copies hold, disagrees with the vote but agrees with it one to three packets' blocks further on does not vote there, and the stretch stays lost — which **Reconstruct lost data** can fill. Of the bytes it leaves out that another day's recording of the page can judge, nearly all were wrong. An incomplete linked series (§5.2.6) is missing a whole record from the middle of its concatenation, whose width is unknown, so it is counted as an appearance but kept out of the vote; one that never received its first record is not delivered at all (see **Records**). A copy damaged only by bit errors still lines up and still votes.
* Not every copy held for a record is a copy of it. §3.2.2 codes the packet address in Hamming 8/4, which corrects one bit error and detects two but resolves a burst silently into a neighbouring codeword, so a packet of some other record is assembled into this one; the identity pass below folds in the copies of identities the recording never named. Such a copy is a clean read of real data, only not of this record, so neither parity nor confidence has anything to say about it — and voting it in makes the record a per-byte blend of both, which for a stateful opcode stream is worse than either alone and worse the more copies there are. What tells it apart is how much of the record it agrees with: copies of one record differ only where they were damaged, a copy of something else disagrees nearly everywhere. So the vote is taken twice, the second time without the copies agreeing with less than half of the first. Only a minority can be dropped that way — where most of them disagree there is no record for the rest to be outliers of, and the vote is left as it was rather than tidied into something that looks decided.
* A copy of the record can also disagree nearly everywhere because its data starts in the wrong place. Where the data begins is read from the record header, whose announcer bytes (§5.2.3, §5.2.7) are Hamming 8/4 like everything else in it, so a misread one claims or disowns a few optional bytes and moves every byte of the copy with them. Before a copy is ruled out, it is tried slid up to eight bytes either way, and one that agrees once slid votes slid. A copy that agrees as it stands is never moved.
* The catalogue holds at most 1,024 records, which is several services' worth. A damaged tape fills it with misread identities long before it holds a thousand pages, so when it is full the least recently seen record no appearance named as transmitted is dropped first, and a record that was named only once none of those is left; the report says the catalogue was truncated. Dropping the least recently seen record of all, a damaged tape lost pages named as transmitted while it held misread identities.
* Sixty-four copies per record are retained for the vote, the most recent sixty-four. On damaged tapes more copies keep helping: against other recordings of the same pages, going from thirty-two to sixty-four puts many times more bytes right than wrong and leaves fewer lost, as going from sixteen to thirty-two did. The cost is memory, and only on a tape that never gives up an undamaged copy of its pages: on the worst measured, the catalogue holds about 10 MB more at its peak than with thirty-two.
* A caption is voted from its own copies and no others: the copies of one run of arrivals, never a copy of an earlier caption that happened to carry the same version (§7.3.10.1). The caption service is bounded at 16,384 captions, each held as its combined bytes. A two-hour captioned recording carries a couple of thousand captions of about a hundred bytes each; the worst case — every caption a full 1,904-byte group (§8.4.2.5), none of whose copies arrived whole — is about 62 MB. Captions past the bound are counted in the report and the records viewer and not kept, so the caption file is the first 16,384 of the service rather than a sample of it.
* Only the combined result is run through the NAPLPS interpreter, never a copy on its own.
* A position no copy ever received is left as NUL. X3.110 §6.1.4 makes that a transparent control with no presentation effect, so a hole costs the drawing nothing beyond the bytes that were actually lost — which is the point of holding the hole open rather than letting the record close up over it.
* Header extension fields (§5.2.8) are decoded, and the More, Next and Index Records they name (meanings 001 to 011) are followed as both receivers of the day followed them, in the forms the receivers took (ES 0, 3, 6, 9 and 12, the sizes the clause's table gives, which is unusable as published — row 12 merges two meanings, and rows 6 and 9 label six- and nine-byte fields as a "Short Record Address"). A field naming a macro (ES 2) is reported and not run. The recommended precapture address (meaning 100) has no use in a catalogue that holds every record already.
* Every run logs a recovery profile at debug level, as part of the report described under `write_report`. It covers how many candidate lines carried a data burst, how many packets came out of each detector, and which gate discarded the rest.

## Choosing the line range

`first_vbi_line` and `last_vbi_line` default to 10-20: where CEA-516 §1.2 permits NABTS, short of the caption line 21 (see **last_vbi_line**). A recording rarely uses all of it, and the lines it does not use are not free: a line carrying another service, or nothing but noise, still produces the occasional 33 bytes whose Hamming 8/4 prefix decodes by chance, and those enter data group reassembly as packets of whatever channel they appeared to name. There they open groups that never complete and consume continuity indices that belonged to real ones.

The report's per-line table is what to read. A line carrying a service shows a large, steady packet count; a line being fitted to noise shows a high burst count and a small packet count. Narrowing the range to the lines that carry the service is worth doing — on the NBC EP transfer above, going from 10-21 to 15-16 took group headers refused from 19691 to 1675, recovered seven more records, and took damage among received record bytes from 0.67 % to 0.57 %.

## Status Indicator

The coloured dot in the top-right corner of the node shows its configuration status.

| Colour | Meaning |
|--------|---------|
| Green | Fully configured and ready to run. All required parameters are set. |
| Yellow | Partially configured. The stage can run but will use default or reduced behaviour — here, no output file is set, so the run fills the **NABTS Records** tool and writes no packet stream. |
| Red | Not configured. One or more required parameters are missing and the stage cannot run. |

Parameters can be set via **Edit Parameters...** in the node context menu. Some stages also provide interactive stage tools (listed under **Tools** above).
